# REFACTOR-TASK — تنظيف كود بلا تغيير سلوك

اسم المشروع `<app>` يُحدَّد في رسالة الجلسة: `modonty` أو `admin` أو `console`. الفرع: `cloud/refactor-<app>`.

## الهدف

نفس التطبيق بالضبط — نفس كل ناتج ونفس كل شاشة — بكود أنظف وأصغر.

## المسموح — هذه الثمانية فقط

| # | التعديل | الشرط |
|---|---|---|
| ١ | فصل المنطق عن الواجهة: استعلام/حساب/تحويل بيانات داخل `.tsx` ← `helpers/` أو `hooks/` أو `actions/` بجانبه، والمكوّن يعرض فقط | نقل حرفي — نفس المدخلات ونفس المخرجات |
| ٢ | حذف الكود الميت (ملف · دالة · تصدير · متغيّر) | دليلان لكل حذف: `knip` + `grep` بلا أي مستورِد، يُكتبان في الـPR |
| ٣ | دمج المكرّر: نفس الدالة في أكثر من ملف ← نسخة واحدة | النسخ متطابقة سلوكاً؛ أي اختلاف ولو بسيط = لا دمج |
| ٤ | تقسيم الملفات الطويلة (> ٣٠٠ سطر) لملفات أصغر | نفس الكود منقولاً |
| ٥ | ترتيب: imports غير مستعملة · أسماء محلّية غير واضحة | داخل الملف فقط |
| ٦ | تقليص الـDOM: `div` تغليف بلا دور (لا class مؤثّرة · لا ref · لا حدث · لا ARIA) يُزال أو يُدمج classه في الأب | الشكل والتفاعل متطابقان بكسل بكسل؛ كل ملف لُمس هنا يُذكر في الـPR للفحص البصري |
| ٧ | الهيكل: تطبيق `.claude/rules/folder-structure.md` حرفياً — ملف مستعمل في مسار واحد ← داخل مجلّد المسار؛ في مسارين ← `<app>/components/shared` أو `<app>/lib` | نقل ملفات وتحديث imports فقط؛ ما ينتمي لـ`shared/` يُكتب في التقرير ولا يُنقل |
| ٨ | أفضل الممارسات: مراجعة بمهارات `.claude/skills/` — `modonty-code-refactor` · `react-best-practices` · `composition-patterns` · `vercel-optimize` · `modonty-naming` · `shadcn` · `web-design-guidelines` + توثيق Next.js الرسمي | يُصلَح ما لا يغيّر الناتج؛ وما يغيّر سلوكاً أو أداءً مرئياً يُكتب في التقرير بملف:سطر ولا يُنفَّذ |

## الممنوع

- تغيير ناتج أي دالة أو استعلام Prisma أو `select` أو ترتيب أو كاش (`"use cache"` · `cacheTag` · `revalidate`).
- تغيير أي نص أو شكل أو رابط أو SEO يراه المستخدم أو جوجل.
- لمس مشروع غير `<app>/` · `shared/` · `shared/prisma/schema` · `package.json` · `pnpm-lock.yaml` · `.env*` · `vercel.json`.
- منطق جديد · ميزة جديدة · مكتبة جديدة · `catch {}` صامت · تغيير أسماء مسارات `app/` (الروابط).
- أي رفع أو PR إلى `main`.

## طريقة العمل

1. **الجرد — بلا أي تعديل:** `<app>/documentation/REFACTOR-PLAN.md` بأرقام وملف:سطر — ملفات `.tsx` التي تخلط المنطق بالعرض · ناتج `knip` · المكرّر · الملفات > ٣٠٠ سطر · أعمق شجرات DOM وأغلفتها الزائدة · مخالفات `folder-structure.md` · مخالفات أفضل الممارسات (البند ٨).
2. **الخطة:** أقسام `app/` مرتّبة من الأقلّ خطراً للأعلى، في نفس الملف.
3. **التنفيذ:** قسم قسم، commit لكل قسم. مسموح تشغيل subagents للأقسام المستقلّة.
4. **التحقّق بعد كل commit:**
   ```bash
   pnpm install
   pnpm --filter ./<app> exec tsc --noEmit
   pnpm --filter ./<app> build
   ```
   صفر أخطاء، وإلا يُرجَع الـcommit.

## التسليم

PR واحد إلى `cloud/refactor-<app>`، وصفه بالعربي:
- الجرد قبل/بعد بالأرقام (ملفات · أسطر · ملفات مختلطة · كود ميت)
- كل ملف محذوف ودليله
- كل ملف لُمس فيه الـDOM (للفحص البصري) · كل ملف نُقل ومكانه الجديد
- قائمة أفضل الممارسات غير المنفّذة (تغيّر سلوكاً) بملف:سطر — للقرار
- ناتج `tsc` و`build` الخام
- الأقسام التي تحتاج تجربة يدوية قبل الدمج
