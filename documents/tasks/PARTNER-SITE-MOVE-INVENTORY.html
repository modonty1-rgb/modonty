السيو

لا يتغيّر رابط ولا canonical ولا JSON-LD ولا خريطة موقع. مشروط ببوّابة واحدة: diff قائمة المسارات قبل/بعد فاضٍ — لو لم يكن فاضياً لا نُكمل.

بعد tsc + بناء + diff روابط + تست حيّ لسبع صفحات + مراجعة على test — الباقي هو ما لا يُرى إلا بحركة حقيقية، وأي شيء منه يُرجَع بكوميت واحد (git revert لكوميت ميكانيكي).

٥ — مخاطر سلوكية يجب التخطيط لها (ليست استيرادات)

  1. ١ الليآوتات: الجذر يحتفظ بـhtml/body/ThemeProvider/SessionProviderWrapper/Trackers. (site)/layout.tsx = TopNav + <main id="main-content" class="flex-1"> + Footer داخل min-h-screen flex-col.   2. ٢ error.tsx/not-found.tsx: الأقرب يفوز. (site) يأخذ النسختين الحاليتين؛ الجذر يبقى فيه not-found.tsx بسيط ببراندنغ مدونتي (يخدم /clients/<slug-غلط> وأي مسار خارج المجموعتين).
  3. ٣ جذر ليآوت واحد فقط (لا ليآوتين جذريين) → لا إعادة تحميل كاملة عند التنقّل بين مدونتي وصفحة الشريك (التوثيق: إعادة التحميل تحدث فقط بين ليآوتات جذرية متعدّدة).
  4. ٤ رابط «تخطّى إلى المحتوى» في TopNav يشير إلى #main-content — يبقى صحيحاً لأن main ينتقل مع TopNav.
  5. ٥ .next بعد النقل الضخم: يُحذف ويُعاد البناء (تجنّباً لأعطال Turbopack المعروفة).
  6. ٦ الفرع: ١٠ ملفات غير مثبَّتة في modonty/ — تُثبَّت في كوميت قبل النقل.

٦ — النطاق الفرعي: هل النقل يفيده؟ نعم، مباشرةً

  • • على kimazone.modonty.com يعيد proxy.ts كتابة الطلب إلى /clients/kimazone/… — يهبط في شجرة (partner) وحدها، فهيدر مدونتي غير موجود أصلاً (لا مخفيّ).
  • • شجرة الشريك المستقلّة تسمح لاحقاً بأن يقرأ ليآوت الشريك وحده المضيف ويخفي شريط مدونتي على النطاق الفرعي — بلا لمس جذر التطبيق ولا صفحات مدونتي.
  • • مع حلّ CSS كان هذا مستحيلاً بلا كشط الجذر. النقل هو ما يفتح باب النطاق الفرعي نظيفاً.

٧ — خطّة كوميت النقل (ميكانيكي، بلا سلوك)

  1. ١. تثبيت العمل الحالي (١٠ ملفات).
  2. ٢. git mv لـ٢٦ مجلّداً + error.tsx + not-found.tsx إلى app/(site)/، وتقسيم clients/.
  3. ٣. إنشاء app/(site)/layout.tsx (TopNav + main + Footer) وتقليص app/layout.tsx.
  4. ٤. استبدال @/app/<segment> → @/app/(site)/<segment> / (partner) (٦٤ + ٣٤ استيراداً).
  5. ٥. حذف .next · tsc صفر · pnpm build.
  6. ٦. إثبات صفر تغيير روابط: diff بين قائمة المسارات قبل/بعد (.next/types/routes.d.ts) وخريطة الموقع = فاضٍ.
  7. ٧. تست حيّ: الرئيسية · مقال · قائمة الشركاء · صفحة شريك · /users/login · صفحة ٤٠٤ · صفحة خطأ.
  8. ٨. دفع إلى modonty-ui → test.modonty.com.

٨ — مراجعة انتقادية للخطّة (١٧ أغسطس، بعد الجرد) — ما كان ناقصاً أو غلطاً

#الاكتشافالأثر لو تجاهلناهالتصحيح في الخطّة
١صفحة ٤٠٤ العامّة كانت غلطاً في الخطّة. توثيق Next: app/not-found.tsx الجذري هو الذي يخدم كل الروابط غير المطابقة في التطبيق، ويُرسم داخل ليآوت الجذر. بعد نقل الهيدر إلى (site) يصير ٤٠٤ أيّ رابط عشوائي بلا هيدر ولا فوتر.رِغرِشن ظاهر لكل زائر يكتب رابطاً غلط.not-found.tsx الجذري يستورد TopNav وFooter ويرسمهما بنفسه (ليس «مبسّطاً»). و(site)/not-found.tsx نسخة لـnotFound() داخل صفحات مدونتي. صفحة شريك بـslug غلط → تصل للجذري (بهيدر مدونتي) ✓.
٢لقطة المسارات قبل النقل لم تكن خطوة صريحة. بوّابة «diff فاضٍ» تحتاج ملفّ «قبل» محفوظاً قبل أوّل git mv (.next/dev/types/routes.d.ts + خريطة الموقع + جدول مسارات pnpm build).بلا «قبل» لا يوجد دليل، والحكم يصير انطباعاً.خطوة ٠ جديدة: حفظ اللقطات الثلاث في documents/tasks/move-snapshot/.
٣معرّفات Server Actions تتغيّر بتغيّر مسار الملف. صفحة مفتوحة قبل النشر ترسل معرّفاً قديماً بعد النشر → خطأ مرّة واحدة حتى إعادة التحميل. يحدث في أي نشر يلمس ملف actions، لكن النقل يلمسها كلّها دفعة واحدة. مؤشّر — يُتحقّق من توثيق Next قبل النشرمستخدمون بصفحات قديمة مفتوحة يرون خطأ لحظياً في أوّل إرسال.النشر في وقت هادئ، والتحقّق من سلوك Next 16 الرسمي؛ لا يمنع النقل.
٤مفاتيح "use cache" مرتبطة بموقع الدالّة → كاش بارد بعد النشر (أوّل طلبات أبطأ).انطباع «الموقع صار أبطأ» عند طارق أوّل دقائق.يُذكر لطارق مسبقاً؛ لا إجراء.
