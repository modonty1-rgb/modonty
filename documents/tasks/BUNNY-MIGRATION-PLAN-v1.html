١ الهدف والمبدأ الذهبي

نقل تخزين كل الصور من Cloudinary إلى Bunny.net، بأداء لا يقل — ويُفضَّل أحسن — وبصفر مخاطرة على الإنتاج (نحن في طور الإنشاء).

المبدأ الذهبي — قراءة مزدوجة (Dual-Read): كل صورة رابطها مخزّن في قاعدتنا. نبني طبقة موحّدة تقرأ مصدر الصورة من host الرابط (cloudinary أو bunny) وتبني التحويل الصحيح لكلٍّ. النتيجة: القديم يبقى شغّالاً والجديد يعمل بالتوازي — لا لحظة كسر واحدة.
  • العمل كله على branch مستقل — الإنتاج الحالي لا يُمَس.
  • تحقّق حي في modonty + admin + قياس أداء بأرقام قبل أي merge.
  • الأصول القديمة على Cloudinary لا تُحذف إلا بعد فترة أمان وتأكيد نهائي.

★ البنية المعتمدة (مُصحَّحة v4) — التوحيد على التخزين، لا على جدول واحد

🔴 تصحيح معماري (بعد قراءة نموذج Reel): الفيديو ليس أصلاً رفيعاً — نموذج Reel كيان محتوى كامل (workflow ٦ حالات · transcript · slug صفحة مشاهدة · counters · ربط بمقال · مراجع Bunny Stream)، مبني صحيحاً بالفعل. دمجه في جدول Media = anti-pattern يدمّره. الصح:
  • Media = أصول رفيعة: صورة + صوت فقط (ملفات على Bunny Storage).
  • Reel = يبقى نموذجه الخاص (فيديو-كمحتوى، Bunny Stream).
  • التوحيد الحقيقي = على التخزين (Bunny): صورة/صوت → Storage · فيديو → Stream. كله Bunny، والسجلّات ليست جدولاً واحداً.

Media = صف واحد لكل أصل (صورة/صوت) بحقل kind، والمحتوى يشير بالـ ID. الصوت greenfield (لا رفع حالياً = بناء جديد، صفر خطر كسر).

Media { // صورة + صوت فقط id kind: IMAGE | AUDIO // لا VIDEO scope, clientId? altText, caption, title, description, license // SEO (موجودة) mimeType, fileSize, createdAt bunnyUrl? // إضافي — يُملأ بالترحيل. url الحي يظل Cloudinary حتى «التبديل» url // رابط الملف على Bunny Storage — محايد width, height // image (موجودة) durationSec? // audio } Article.audioMediaId → Media (بناء جديد — بدل audioUrl النص) Client.logoMediaId / heroImageMediaId → Media (موجودة) Reel { } // يبقى نموذجه الخاص — فيديو على Bunny Stream (لا يُدمج) bunnyVideoId · playbackUrl · mp4Url · thumbnailUrl · transcript · workflow · slug · counters
الفيديو ≠ الصورة/الصوت (متحقّق من docs.bunny.net): الفيديو على Bunny Stream (منتج منفصل). بعد الرفع تحصل على guid + libraryId فقط، وكل روابط التسليم تُشتَق:
  • HLS: https://{zone}.b-cdn.net/{guid}/playlist.m3u8
  • MP4: .../{guid}/play_1080p.mp4
  • Embed: https://iframe.mediadelivery.net/embed/{libraryId}/{guid}
  • Thumbnail: .../{guid}/thumbnail.jpg
فالفيديو لا نخزّن له url ملف — نخزّن المعرّف ونشتق الباقي في دالة. ريلز مودونتي أصلاً كذا (Reel.bunnyVideoId). ولأن الفيديو أصلاً على Stream = لا Cloudinary فيه، فلا يُرحَّل — فقط يندمج في Media الموحّد.
الأثر على الترحيل: الصور + الصوت فقط يُرحَّلون Cloudinary → Bunny Storage (نمط url + cloudinaryBackupUrl). القراءة لا تتغيّر لأن الحقل url محايد أصلاً. الفيديو يُدمَج معمارياً بلا ترحيل تخزين.

★ حيلة السرعة — تسخين الصور المسبق (Image Prefetch) · مدروسة من NextFaster

دراسة كاملة لمقاربة مشروع NextFaster في تسريع الصور، بهدف تطبيقها على مدوّنتي بشكل أفضل مما طبّقوها. مستقلة تماماً عن التخزين — تشتغل مع Cloudinary الآن ومع Bunny بعد الترحيل بلا فرق.

ما الحيلة؟ تسخّن الصورة الرئيسية للصفحة الجاية قبل الضغط عليها — فتُفتح الصفحة وصورتها ظاهرة فوراً بلا وميض تحميل. المصدر: مشروع NextFaster (متجر Next.js شهير بأداء عالٍ على مليون صورة/مليون زيارة).
🔑 التمييز الجوهري (لا تُنسَ): الحيلة تحسّن سرعة التنقّل بين الصفحات، لا سرعة أول فتحة للموقع. أول فتحة تتحسّن بأشياء أخرى (جودة منخفضة متعمّدة · أول صور eager · أبعاد صحيحة · avif). الحيلة تلمع في مسار: قائمة → مقال → مقال.

الـ flow خطوة بخطوة

1 · viewportالرابط يدخل الشاشة (threshold 0.1) → بعد 300ms: router.prefetch(route) + جلب قائمة صور الهدف (JSON رخيص) وتخزينها في imageCache. لا تسخين بايتات بعد.
2 · hoveronMouseEnter → router.prefetch مجدداً + تسخين البايتات فعلياً عبر prefetchImage() لكل صورة في القائمة (نية أقوى).
3 · mousedownpreventDefault + router.push → الملاحة تبدأ قبل رفع الإصبع (mouseup/click).
4 · clickالصفحة تفتح وصورها محمّلة مسبقاً في كاش المتصفح → ظهور فوري بلا وميض.
لماذا مرحلتين؟viewport يبني القائمة الرخيصة (JSON مكاش)، وhover يسخّن البايتات الثقيلة (إشارة نية أقوى) → لا هدر باندويث على كل رابط ظاهر.

كيف نطبّقها أحسن منهم — تحسينات Senior على واقع كودنا

#تطبيقهم (نقطة ضعف)تطبيقنا الأفضل
1endpoint يجيب HTML كامل + parse — استدعاء وظيفة لكل صفحة هدف + اعتماد هشّ على parse الـ DOM.أنظف نعرف صورة المقال من قاعدتنا (featuredImage.url + width/height) → endpoint خفيف يرجّع الروابط من DB مباشرة (أو نمرّرها مع بيانات البطاقة). بلا جلب HTML، بلا parse.
2يسخّن كل main img — يهدر باندويث على صور تحت الطية.نسخّن الـ LCP فقط (الصورة الرئيسية للمقال) — تحكّم دقيق.
3يتجاهل الشبكات البطيئة — يسخّن على 2G وData Saver.مهم نحترم navigator.connection.saveData + effectiveType (2g/slow-2g) → نتخطّى التسخين.
4⚠️ أخطر نقطة — مطابقة مفتاح الكاش بالضبط: صورة التسخين لازم تطابق الرِندَر حرفياً (/_next/image?url&w&q) وإلا تحميل مزدوج والحيلة تنقلب ضرراً. عندنا OptimizedImage.clampQuality يقرّب الجودة لأقرب قيمة من [25,50,75,100] (مثلاً 65 → 75) → التسخين لازم يمرّر نفس quality/sizes عبر getImageProps. نتحقق: طلب واحد فقط لكل صورة في تبويب Network.
5—نحافظ على ترتيب sizes → srcset → src (شرط تقني لا يتغيّر).
6—سقف التسخين: أول N روابط · أو hover-only على الموبايل (اللمس ≠ hover).
7—fetchPriority=low + decoding=async — لا نزاحم موارد الصفحة الحالية.
8نرفض: typescript.ignoreBuildErrors:true (ينشرون بأخطاء TS) + خطف الملاحة onMouseDown preventDefault (يكسر فتح تبويب جديد/إمكانية الوصول).انتقائي نبقى strict · نبدأ بدون خطف الملاحة ونقيس أولاً؛ نضيفه فقط لو أثبت القياس قيمته.

واقع مدوّنتي (بدليل من الكود)

  • @/components/link حالياً wrapper بسيط بـ prefetch={false} → حتى prefetch الـ route معطّل الآن. الحيلة تحتاج بناء Link مخصص كامل.
  • components/feed/ArticleCard.tsx نصّية بلا صورة → هدف التسخين = الصورة الرئيسية داخل صفحة المقال (الـ LCP)، لا صورة بطاقة.
  • Media فيه width/height (schema سطر 1252-1253) → أبعاد حتمية متاحة عندنا (ميزة على NextFaster الذي يستخرجها من HTML).
  • next.config: formats: [avif, webp] · qualities: [25,50,75,100] · deviceSizes مضبوطة → أساس جاهز، والحيلة تُبنى فوقه.

#الثغرةالأثر / العلاج
1كاش الـ SEO يحمل روابط Cloudinary محفورة — jsonLdStructuredData + nextjsMetadata مخزّنة في القاعدة (مقال·عميل·تصنيف·صناعة) وفيها روابط الصور القديمة. تبديل url/socialImage لا يحدّثها.الأخطر بعد الترحيل JSON-LD/OG يظلّان يشيران لـ Cloudinary. العلاج: مرحلة إعادة توليد SEO لكل كيان متأثّر (زي دمج الوسوم). بدونها = روابط سيو ميتة عند الإطفاء.
2«Optimizer غير مطلوب» ناقص — صحيح لصور next/image فقط. صور OG/الكراولر + أي <img> خام + صورة JSON-LD لا تمرّ عبره وتعتمد تحويلات Cloudinary محفورة.تدقيق إمّا نرفع OG بمقاس نهائي 1200×630 مسبقاً (يشيل الحاجة)، أو نحتاج Optimizer لها. يجب فحص: هل OG مُسبقة المقاس؟ وهل يوجد <img> خام؟
3تناقض داخلي في face_crop — face_crop ميزة Optimizer، والخطة تلغي Optimizer.مُصحّح الأفتار = قص مركزي عادي (أثر مهمل). حُدّث في الجدول أعلاه.
4«أرخص/أسرع» لم يُثبَت بأرقام — أُثبت أن التخزين رخيص فقط.أرقام ناقصة باندويدث Bunny متحقّق (من $0.002/GB ✓)، لكن فاتورة Cloudinary الحالية وتكلفة صور Vercel (تبقى مع next/image وقد تفوق ثمن Optimizer) — غائبتان. قرار «بلا Optimizer» قد يطلع أغلى حتى نجيب رقم Vercel.

12ماسح أيتام Cloudinary لغم — sweepCloudinaryOrphans (cloudinary-orphans.ts:194 uploader.destroy) يحذف أصول Cloudinary غير المرجعية. بعد الترحيل القاعدة تشير لـ Bunny → كل أصول Cloudinary تصير أيتام → يحذف نسخ الرجوع.حرج يُعطَّل الماسح طوال الترحيل + نافذة الأمان. (الحساب مشترك — بالتعليق نفسه.)
13deleteMedia لا يعرف Bunny — يحذف عبر cloudinaryPublicId فقط (delete-media.ts:47). أصول Bunny بلا publicId → الحذف يترك يتيماً على Bunny.تحديث الحذف ليدعو deleteBunnyUrl لروابط Bunny.
14remotePatterns — admin بلا أي host بَني (*.cloudinary.com فقط). console/modonty فيهما reels فقط.الثلاثة تحتاج زونات Bunny (clients+assets). بلوكر اختبار لكل تطبيق — مبكراً.
15الترحيل لازم يجيب الأصل — الـ url المخزَّن يحمل f_auto,q_auto,w_auto محفورة (image-seo.ts). نسخ الرابط المحوّل = نسخ derivative لا الأصل.السكربت يجيب الأصل من Cloudinary (عبر publicId/تجريد التحويل) ويرفعه لـ Bunny.
16تراجع JSON-LD متعدد النِّسب — buildAspectUrl يولّد 1:1·4:3·16:9 لنتائج Google الغنية (توصية). Bunny بلا Optimizer → النسبة المخزّنة فقط.سيو طفيف نبني النِّسب وقت الرفع (أصول متعددة) أو نقبل نسبة واحدة (مقبول عند Google).
17الصورة الافتراضية تُفقد — d_article-placeholder-default (Cloudinary) بلا مقابل في Bunny → صورة مكسورة تظهر فارغة.fallback في الكود (onError/placeholder محلي).
18نمط الرفع يختلف — Cloudinary رفع مباشر من المتصفح (unsigned preset، use-cloudinary-upload.ts). Bunny مُوكَّل عبر السيرفر (حد Vercel ~4.5MB) + الفيديو TUS resumable.تغيير معماري في الرفع + مراعاة الحد. الفيديو مسار TUS منفصل.
19🔴 الفيديو لا يُدمَج في Media — Reel كيان محتوى غنيّ (workflow·transcript·slug·counters)، دمجه anti-pattern.مُصحَّح أعلاه Media = صورة+صوت · Reel يبقى · التوحيد على التخزين فقط.
20الصوت greenfield — audioUrl حقل نص يُلصَق، لا رفع.توحيده = بناء جديد (Media kind=AUDIO)، لا ترحيل. صفر خطر كسر.
21thumbnails الأدمن من publicId — thumbnail-image-view.tsx:129 يبني رابط Cloudinary من cloudinaryPublicId لا url.تحديث لدعم Bunny (via url + next/image).
22قرّاء الرابط server-side — image-sitemap + OG + JSON-LD تقرأ الرابط من القاعدة. عند «التبديل» لو ما قرأت الحقل الجديد → sitemap يشير Cloudinary والصفحة Bunny = تضارب.تُحصر وتُحدَّث عند التبديل (SEO regen موجود · sitemap + OG صريحة).
23kind يتشعّب في واجهة المكتبة — مبنية للصور (thumbnail/نسبة/picker) → صفوف AUDIO تكسر الافتراضات.تفريع الواجهة حسب kind.
خبر جيد (مؤكّد بالكود): دوال إعادة توليد SEO موجودة وجاهزة (regenerateArticleJsonLd · regenerateClientJsonLd · generateAndSave{Category,Industry,Tag}Seo · regenerateNextjsMetadata) → «التبديل» (الثغرة 1) يُنفَّذ بأدوات قائمة، لا بناء من صفر. ومواقع التحويل الحيّة كلها تتجاهل روابط Bunny بأمان (تُرجعها كما هي) → صور الصفحة لا تنكسر.

٥ الخطة بالمراحل — بوّابات أمان بين كل مرحلة

المرحلة 0 — قياس + أساس بيانات (بلا كود إنتاج) تعالج 4·5·7·8·10

الهدفنثبت أن Bunny ≥ Cloudinary أداءً وتكلفةً، ونعرف الحجم قبل أي التزام.
الأداءرفع 3 صور عيّنة إلى Bunny + إضافة host الزون لـ remotePatterns (بلوكر) · عرض عبر next/image · قياس LCP + أول بايت + حجم مُقدَّم، Bunny مقابل Cloudinary.
التكلفة3 أرقام: فاتورة Cloudinary الحالية · تكلفة تحسين صور Vercel الحالية (تحسم هل Optimizer أرخص فعلاً) · تسعير Bunny Stream (للفيديو).
الحجمعدّ صفوف Media + إجمالي GB → يحسم «تدريجي مقابل دفعة» + بيت زون صور المقالات.
بوابةلو Bunny ليس أفضل/مساوٍ أداءً وتكلفةً → نتوقف. لا نكمل.

المرحلة 1 — تدقيق طبقة التحويل + مسارات OG/الخام تعالج 2

الهدفضمان أن روابط Bunny تمرّ نظيفة، وأن OG لا تنكسر.
العملoptimizeCloudinaryUrl يتجاهل روابط Bunny أصلاً — لا تغيير. لكن نفحص: (أ) هل صور OG/socialImage مُسبقة المقاس 1200×630 أم تعتمد تحويل محفور؟ (ب) هل يوجد <img> خام يحقن transform Cloudinary؟ · نتأكد أن knowledge-graph-generator يتعامل مع host غير Cloudinary بأمان.
التحقّقروابط Bunny تخرج كما هي؛ OG صحيح لصورة Bunny.
بوابةtsc صفر + JSON-LD/OG صحيح لصورتَي Bunny وCloudinary.

المرحلة 2 — الرفع الجديد → Bunny

الهدفكل رفع جديد للمكتبة الرئيسية يذهب Bunny.
العملتوجيه رفع Media (نفس نمط upload-bunny الموجود) + تخزين رابط Bunny. القديم يبقى Cloudinary.
التحقّقالدائرة: admin رفع → عرض modonty → JSON-LD → OG صحيحة.
بوابةصورة مرفوعة حديثاً تظهر صحيحة في الثلاثة (admin/modonty/JSON-LD).

المرحلة 3 — ترحيل إضافي بحت (لا يمسّ الإنتاج) آمن على أي قاعدة

العملسكربت: ينسخ الأصل → Bunny · يكتب الرابط في حقل bunnyUrl الجديد فقط · دفعات + تقرير. لا يلمس url الحي · لا يعيد توليد SEO · لا يحذف من Cloudinary.
لماذا آمنكتابة إضافية على حقل يتجاهله الإنتاج → الإنتاج يظل يقرأ url (Cloudinary) بلا أي تأثير، حتى لو رُكِّب على القاعدة المشتركة.
قبل التشغيلاطبع DATABASE_URL وأكّد أنها ليست إنتاج · عطّل ماسح أيتام Cloudinary (ثغرة 12) · idempotent · يجيب الأصل من Cloudinary لا المحوّل (ثغرة 15) · يحسب الأبعاد (ثغرة 11).
بوابةbunnyUrl مملوء لكل الصفوف · كل روابط Bunny تُرجع 200.

المرحلة 3.5 — «التبديل» المتحكَّم به (الخطوة الوحيدة التي تمسّ الإنتاج) تعالج 1·9

الشرطلا تبدأ إلا بعد نجاح كل الاختبار على الفرع + الكود المنشور يقرأ bunnyUrl.
العمل(1) باكب DB أولاً. (2) الكود يقرأ bunnyUrl ?? url. (3) إعادة توليد SEO لكل كيان متأثّر (jsonLdStructuredData + nextjsMetadata) لتشير لـ Bunny — وإلا تبقى Cloudinary في الكاش.
الرجوعفوري: الكود يرجع لقراءة url + إعادة توليد SEO. bunnyUrl يبقى، لا نخسر شيئاً.
بوابةلا حذف Cloudinary · JSON-LD/OG على Bunny · فاحص 200 يمرّ 100%.

المرحلة 4 — تحقّق شامل + merge إلى main (آخر خطوة)

العملتتبّع الدائرة كاملة · قياس أداء نهائي · remotePatterns للثلاثة · فاحص شامل «كل الصور 200» يمرّ على كل Media.url + socialImage (تعالج 6).
بوابة الـ mergeالأربعة معاً: (1) أداء أفضل مُثبَت · (2) فاحص 200 يمرّ 100% (صفر صورة مكسورة) · (3) JSON-LD/OG على Bunny · (4) صفر console errors. أي واحدة تفشل → يبقى على الفرع.

مرحلة مستقلة (يمكن الآن) — حيلة تسخين الصور + قياس لا تعتمد على Bunny

الهدفتنقّل فوري بين صفحات المقالات/الشركاء — الصورة الرئيسية جاهزة قبل الضغط.
العملبناء Link مخصص (IntersectionObserver + hover) · تسخين الـ LCP فقط عبر getImageProps بنفس quality/sizes الرِندَر · احترام saveData/effectiveType · ترتيب sizes→srcset→src · fetchPriority=low.
بدونبدون /api/prefetch-images (نجيب صورة المقال من DB) · بدون خطف mousedown في النسخة الأولى.
التحقّققياس LCP المُحسّ للتنقّل قبل/بعد · صفر تحميل مزدوج (فحص طلبات /_next/image في Network — طلب واحد لكل صورة).
بوابةLCP التنقّل أفضل بأرقام + صفر تحميل مزدوج + صفر console errors. وإلا لا نبقيها.

المرحلة 5 (لاحقاً) — إيقاف Cloudinary

العملبعد فترة أمان: حذف أصول Cloudinary + تنظيف الكود + إزالة مفاتيح Cloudinary.
