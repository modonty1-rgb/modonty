بنية المسارات

المبدأ الحاكم واحد: كل صفحة لها مجلد، وكل شي يخصها داخل مجلدها. تبي تعدّل في صفحة المنتجات؟ تفتح مجلدها وتلقى مكوّناتها ومساعداتها وإجراءاتها. ما تدور في المشروع كله.

هذا سليم تماماً في موجّه التطبيقات، لأن المجلد وحده لا ينشئ مساراً — الصفحة هي اللي تنشئه. يعني مجلدات المكوّنات والمساعدات تسكن داخل مجلد المسار بلا أي أثر على العنونة، وبلا حاجة لبادئة تخفيها.

ومقطع اللغة لا يغيّر شيئاً من هذا. بعض مشاريعك فيه مقطع لغة وبعضها ما فيه، والترتيب تحته هو نفسه حرفاً بحرف. المهم إن القواعد وأنماط المنع مكتوبة بصيغة لا تفترض وجوده ولا غيابه، فتشتغل في الحالتين. والقاعدة الوحيدة المرتبطة به: تتبع ما يفعله المجلد اللي تشتغل فيه، وما تضيف مقطعاً ولا تحذفه من عندك، وما تكتب رمز اللغة في أي مسار أو رابط يدوياً.

القاعدة الوحيدة اللي تُبقي هذا حياً

الشجرة المرتبة تنهار خلال شهرين إذا ما فيه قانون يمنع الاختراق. القانون ثلاثة أسطر: المسار يسحب من المشترك، والمشترك لا يسحب من أي مسار أبداً، ومسار لا يسحب من مسار ثاني إطلاقاً. لو احتاج مسار شيئاً من مسار ثاني، فهذا إشعار ترقية إلى المشترك، لا مبرر لاستيراد مباشر.

والترقية لها شرط، وإلا صار المجلد المشترك مقبرة مكوّنات يستعملها مسار واحد: مستهلكان حقيقيان في مسارين مختلفين، ويتغيران معاً. وإذا رجع المكوّن المشترك لمستهلك واحد، ينزل مرة ثانية لمجلد مساره.

# Folder structure

## Where a file goes — there is no third option
- Used by ONE route  → inside that route's folder.
- Used by TWO OR MORE routes → the shared folder.

## Route folder layout
app/<route>/
  page.tsx        server component, thin: fetch + compose
  loading.tsx     skeleton matching the real layout
  error.tsx       only where the route can realistically fail
  components/     used by this route only
  helpers/        hooks, utils, zod schemas, types — this route only
  actions.ts      server actions for this route only

## Shared layout
components/ui/       shadcn primitives. No business logic, no app types, no data.
components/shared/   composed components used by two or more routes.
helpers/             utils used by two or more routes.

## Import direction — never violated
- A route MAY import from components/ui, components/shared, helpers.
- Shared code MUST NOT import from any route folder. Ever.
- A route MUST NOT import from another route's folder. Ever.
If route A needs something from route B, promote that thing to shared first.
Never import across routes, not even temporarily.

## Promotion rule
Promote only when BOTH are true:
1. two real consumers, in two different routes
2. they change together — one edit serves both
Never promote on first use "because it might be reused later".
If a shared component drops back to one consumer, move it back into that route.

## Imports style
- Inside a route: relative imports (`./components/Card`).
- To shared code: the alias (`@/components/shared/Card`).
An alias import pointing into `app/` is the signal that a boundary was crossed.

## Naming
Folders are `components` and `helpers`. No underscore prefix — a folder without
page.tsx does not create a route, so nothing needs hiding.

لو صار عندك أكثر من تطبيق

لا تنقل مشاريعك إلى مستودع موحّد اليوم. التكلفة حقيقية — إعدادات بناء وتخزين مؤقت وتكامل مستمر ونشر — والمكسب لا يظهر إلا لما يوجد كود مشترك فعلي يتكرر ويتغيّر مرتين. علامة الانتقال واضحة: تعدّل نفس المكوّن يدوياً في مشروعين في نفس الأسبوع. قبل هذي اللحظة، الترتيب أعلاه كافٍ.

الاستعداد للانتقال ما يكلفك شيئاً اليوم، وشرطه واحد: يبقى مجلد البدائيات البصرية نظيفاً تماماً من أنواع مشروعك ومن قاعدة بياناتك. إذا التزمت بهذا، فاستخراجه لاحقاً عملية نقل مجلد، لا إعادة كتابة. وإذا تلوّث، فالانتقال يصير مشروعاً بحد ذاته.

ولما تجي اللحظة، عندك مساران: مستودع موحّد يجمع التطبيقات مع حزم مشتركة، وهو الأنسب إذا كنت تعدّل التطبيقين وتنشرهما معاً؛ أو حزمة خاصة منشورة تستهلكها المستودعات المنفصلة، وهي الأخف إذا كان كل مشروع يمشي بإيقاعه ودورة إصداره. هذا شكل الأول:

خطة نقل مشروع قائم

كل ما سبق مصوغ بصيغة «اكتب هكذا»، وهي لا تكفي لمشروع قائم فيه آلاف الأسطر. ولنكن دقيقين في الوعد: الأمان الكامل غير موجود في أي إعادة هيكلة. الموجود والقابل للتحقيق شيء آخر وأفيد — أن يكون كل تغيير قابلاً للإرجاع بأمر واحد، وقابلاً للإثبات بمقارنة آلية. هذي الخطة تبني هذين، لا وعداً بالعصمة.

والقاعدة اللي تسبق كل شي: ممنوع منعاً باتاً أن يُطلب من النموذج «أعد هيكلة المشروع». هذا الطلب ينتج تغييراً بمئات الملفات لا تقدر تراجعه ولا تعرف وين انكسر. النقل يتم مساراً واحداً في كل مرة، وكل مسار في فرع مستقل يُدمج وحده.

القواعد غير القابلة للتفاوض أثناء النقل

  • لا تغيير سلوك مع تغيير مكان. النقلة تحرّك ملفات وتصلّح مسارات الاستيراد فقط. أي تحسين أو إصلاح أو إعادة تسمية يأتي في تغيير منفصل بعد استقرار البنية.
  • النقل بأمر التحريك لا بالنسخ والحذف، عشان يبقى تاريخ الملف متصلاً وتقدر تتبع من كتب ماذا ومتى.
  • مسار واحد لكل فرع، وفرع واحد لكل دمج. لو انكسر شي، الإرجاع أمر واحد يمسّ مساراً واحداً.
  • العلامة الفارقة في المراجعة: ملخّص التغيير لازم يكون نقل ملفات وأسطر استيراد فقط. أي سطر منطق تغيّر داخل نقلة بنيوية هو خطأ يُرد، مهما بدا التحسين مغرياً.
  • التنبيهات تبقى تنبيهات حتى النهاية. هنا تظهر قيمة اختيارك السابق: لو كانت الحدود أخطاء موقفة للبناء، لما قدرت تنقل مساراً واحداً في مشروع فيه مئة اختراق قائم.
فخ يخصّك أنتتغيير حالة حرف في اسم ملف — من كبير إلى صغير أو العكس — لا يُسجَّل على ويندوز لأن نظام ملفاته لا يفرّق، فيمر التغيير عندك ولا يصل للمستودع، ثم ينكسر البناء على الخادم. لو احتجت تصحيح حالة اسم أثناء النقل، تُنفَّذ على خطوتين عبر اسم وسيط مؤقت. هذي تصيب كل من يهاجر بنية من جهاز ويندوز.

اللقطة: كيف تثبت أنك ما كسرت شيئاً

ما عندك مجموعة اختبارات، وبناء هذي المجموعة الآن يؤخّر النقل شهوراً. البديل العملي لمنصة محتوى: تلتقط ناتج الصفحات المهمة قبل النقل، وتقارنه بعده. المقارنة على الناتج المُطبَّع — بعد إزالة معرّفات البناء والقيم المتغيّرة — فأي فرق حقيقي يظهر فوراً وأي ضجيج يختفي.

./scripts/route-snapshot.mjs
// Capture, then compare, the rendered HTML of the routes that matter.
//   node scripts/route-snapshot.mjs capture
//   node scripts/route-snapshot.mjs compare
// Run against a local production build, not the dev server.

import { mkdirSync, writeFileSync, readFileSync, existsSync } from "node:fs";
import { createHash } from "node:crypto";

const BASE = process.env.SNAPSHOT_BASE ?? "http://localhost:3000";
const DIR = ".snapshots";

// Add every route you cannot afford to break. Keep it short and real.
const ROUTES = ["/", "/about", "/blog", "/pricing"];

// Strip what legitimately changes between builds.
const normalise = (html) =>
  html
    .replace(/<script[^>]*>[\s\S]*?<\/script>/g, "")
    .replace(/nonce="[^"]*"/g, "")
    .replace(/\/_next\/static\/[^"']+/g, "/_next/static/BUILD")
    .replace(/data-reactroot="[^"]*"/g, "")
    .replace(/\s+/g, " ")
    .trim();

const digest = (text) => createHash("sha256").update(text).digest("hex");

const collect = async () => {
  const result = {};
  for (const route of ROUTES) {
    const res = await fetch(`${BASE}${route}`);
    const body = normalise(await res.text());
    result[route] = { status: res.status, hash: digest(body), length: body.length };
  }
  return result;
};

const mode = process.argv[2];
const file = `${DIR}/routes.json`;

if (mode === "capture") {
  mkdirSync(DIR, { recursive: true });
  writeFileSync(file, JSON.stringify(await collect(), null, 2));
  console.log(`Captured ${ROUTES.length} routes to ${file}`);
  process.exit(0);
}

if (mode === "compare") {
  if (!existsSync(file)) {
    console.error("No baseline. Run capture on the pre-migration build first.");
    process.exit(1);
  }
  const before = JSON.parse(readFileSync(file, "utf8"));
  const after = await collect();
  const changed = ROUTES.filter(
    (r) => before[r]?.hash !== after[r].hash || before[r]?.status !== after[r].status
  );
  if (changed.length === 0) {
    console.log("Identical output on every route. The move was structural only.");
    process.exit(0);
  }
  for (const r of changed) {
    console.error(`CHANGED ${r}  status ${before[r]?.status} -> ${after[r].status}  length ${before[r]?.length} -> ${after[r].length}`);
  }
  process.exit(2);
}

console.error("Usage: node scripts/route-snapshot.mjs capture|compare");
process.exit(1);

files moved · imports rewritten · boundary warnings before and after ·

ما يُوحَّد وما لا يُوحَّد

هذي أهم تفرقة في الموضوع كله، وتجاهلها هو ما يحوّل التوحيد من مكسب إلى عبء. البدائيات تُوحَّد. المكوّنات التي تعرف نطاق منتجك لا تُوحَّد.

يُوحَّديبقى داخل التطبيق
الزر، الحقل، النافذة، القائمة، البطاقة، التنبيه — أي عنصر لا يعرف شيئاً عن منتجكأي مكوّن يعرف نموذج بيانات، أو مفتاح ترجمة، أو مسار تنقّل، أو صلاحية مستخدم
دالة دمج الأصناف، وخطافات عامة كخطاف حجم الشاشةجدول بيانات لوحة الإدارة، وبطاقة المقال في الموقع، ونموذج الاشتراك
الرموز التصميمية: الألوان والمسافات والخطوط ونصف القطرأي شي يتغيّر لسبب يخصّ تطبيقاً واحداً
الفخ الذي يجعل التوحيد أسوأ من التكرارلو كان زر لوحة الإدارة يختلف عمداً عن زر الموقع، فتوحيدهما في مكوّن واحد ينتج راية شرطية جديدة عند كل اختلاف، ثم راية فوق راية. هذا بالضبط ما يمنعه مبدأ «مفتوح للتوسعة مغلق للتعديل» في هذا الملف. الاختلاف المقصود ليس تكراراً، وتوحيده خطأ لا إصلاح.

الاختبار الذي يحسم القرار قبل أي نقل

لا تقرر من الذاكرة. قارن النسخ الثلاث لكل مكوّن، وصنّفها في ثلاث خانات فقط:

  • متطابقة — تُوحَّد فوراً، بلا نقاش.
  • مختلفة اختلافاً عرضياً — نسخة أقدم من أخرى، أو مسافة بادئة، أو إصلاح طُبّق في واحدة فقط. تُوحَّد على أحدث نسخة، ويُوثَّق ما ضاع.
  • مختلفة اختلافاً مقصوداً — تبقى منفصلة حتى تقرر أنت هل الاختلاف مطلوب فعلاً. لو كان مطلوباً، فليس تكراراً. لو كان انحرافاً غير مقصود، وحّده ثم انقله.

هذي الخانات الثلاث هي مخرج المرحلة الأولى، وهي وثيقة تراجعها أنت قبل ما يُنقل حرف واحد.

الفرق بين ثلاثة مستودعات وثلاثة تطبيقات — وهو فرق حاسم

لو كانت التطبيقات الثلاثة داخل مستودع واحد، فالتوحيد رخيص: حزمة محلية مرتبطة بمساحة العمل، والتعديل فيها يظهر في التطبيقات الثلاثة فوراً بلا نشر ولا إصدار. وهذي هي الحالة التي يدعمها مولّد المكتبة رسمياً.

ولو كانت مستودعات منفصلة فعلاً، فالتوحيد يعني حزمة تُنشر وتُصدَّر وتُرقَّى في ثلاثة أماكن، وكل تعديل صغير يصير دورة نشر. في هذي الحالة، المكسب أقل من التكلفة إلا إذا كان عدد المكوّنات المشتركة كبيراً واستقرارها عالياً. والقرار العملي غالباً: اجمع التطبيقات الثلاثة في مستودع واحد أولاً، ثم وحّد المكتبة — لا العكس.

ملف التعليمات الرئيسي

هذا الملف يُحقن في سياق كل جلسة كرسالة، مو كأمر نظام. يعني النموذج يقرأه ويحاول يلتزم، لكن ما فيه ضمان صارم. ثلاث قواعد تحكم فعاليته: يكون تحت مئتين سطر، وكل بند فيه قابل للتحقق حرفياً، وما فيه تعليمات متناقضة — لأن التناقض يخلي النموذج يختار عشوائياً.

القسم الأهم فيه هو انضباط النطاق. الكود العشوائي والتضخم والتعقيد ما سببهم جهل النموذج بالممارسات، سببهم إنه ما محدد له حدود التعديل، فيروح يحسّن أشياء ما طلبتها ويبني تجريدات ما تحتاجها.

وقاعدة واحدة تحكم توزيع كل ما يلي: القاعدة تُكتب في مكان واحد فقط. إغراء تكرارها في الملف الرئيسي وفي ملف القواعد وفي المهارة وفي وكيل المراجعة قوي — يبدو تأكيداً نافعاً. لكنه ليس كذلك: أول تعديل تسويه على قاعدة راح ينسى موضعين منها، فتصير عندك تعليمات متناقضة، والتناقض يخلي النموذج يختار عشوائياً وهذي أسوأ من غياب القاعدة أصلاً. لذلك الملف الرئيسي يحمل ما يسري على كل ملف بلا استثناء، والباقي يعيش في ملفات القواعد المشروطة، ووكيل المراجعة يقرأها بدل ما ينسخها.

وسطر المكدّس في أوله ليس زينة: النموذج يبني عليه كل قرار لاحق. لذلك يذكر ما تستعمله اليوم فقط، ويسمّي صراحة ما هو مخطط له ولم يُعتمد بعد — وإلا استعمله النموذج في جلسة ونسيه في التي بعدها.

# React & UI Rules

## Component responsibility
- A component either FETCHES or RENDERS. Never both in one file.
- Over ~150 lines, split it. The split is by responsibility, not by line count:
  extract the part that has its own reason to change.
- Presentational components receive data as props and own no data logic.

## Client boundary
- `"use client"` requires a comment on the line below naming the reason:
  `// client: uses useState for the open/closed panel`
- Never mark a page or layout as a client component to "make an import work".
  Move the interactive part into its own leaf component instead.

## Props
- Pass the fields you render, not the whole entity.
  `<UserCard name={u.name} avatar={u.avatar} />` — not `<UserCard user={u} />`
  unless the component genuinely renders most of the entity.
- No boolean flag chains. Three or more booleans that describe one dimension
  become a single union prop: `state: "idle" | "loading" | "error"`.
- No `variant` prop implemented as an if/else ladder. Use a lookup object:
  `const styles = { primary: "...", ghost: "..." } as const`

## State
- No `useState` for anything derivable from props or from other state.
- No `useEffect` to sync state — derive it during render.
- `useEffect` is allowed only for: subscriptions, browser APIs, and cleanup.
  Every `useEffect` gets a one-line comment saying which of the three it is.
- No `useMemo` / `useCallback` without a measured reason. Premature memoization
  adds dependency bugs and hides nothing.

## Layout
- Mobile-first. Verify the layout at 375px width before desktop.
- RTL is the primary direction. Use logical properties: `ms-`, `me-`, `ps-`, `pe-`,
  `start-`, `end-`, `text-start`, `text-end`, `border-s`, `border-e`.
  Never `ml-`, `mr-`, `pl-`, `pr-`, `left-`, `right-` on anything a user reads.
- Tailwind v4. Design tokens are declared in the global stylesheet with `@theme`,
  not in a JS config. Add a token there before using a custom value.
- Tailwind classes only. No inline `style` unless the value is dynamic at runtime.

## Accessibility floor — not optional
- Every interactive element is reachable by keyboard and has a visible focus ring.
- Every icon-only button has an `aria-label` with an Arabic string from i18n.
- Images have `alt`. Decorative images get `alt=""`.

## Strings
- No hardcoded user-facing string. Every string is a translation key present in
  BOTH ar and en in the same change.
- Arabic UI copy contains no Latin words.
Full Arabic rules: .claude/rules/i18n-arabic.md

## Loading — granularity matters more than existence
`loading.tsx` wraps the WHOLE segment in one boundary: the entire page becomes a
skeleton until the slowest call finishes, including the parts that were ready
immediately. That is the wrong default for LCP.
- Prefer a `<Suspense>` boundary around the slow part only, so the static shell
  ships instantly and the slow region streams in behind it.
- Use `loading.tsx` when the whole segment genuinely depends on one fetch, or as
  a first pass before the boundaries are placed.
- Either way the fallback mirrors the real layout: same block count, same rough
  sizes. A centered spinner is not acceptable — it causes layout shift.

## Pushing the client boundary down
When a client component needs server-rendered content inside it, pass that
content as `children` from a server parent. The child stays on the server and
out of the bundle. Do not import a server component into a client component.

```
// server parent
<Accordion>          {/* client */}
  <ProductDetails />  {/* stays server-rendered */}
</Accordion>
```

## Fonts and third-party scripts
- Fonts through `next/font` only, and the Arabic subset must be requested
  explicitly — a Latin-only subset silently falls back and wrecks Arabic
  rendering. Verify the weights you set actually exist in the Arabic face.
- Third-party scripts through `next/script`. Nothing analytics-related loads
  before the page is interactive; a tag manager loading eagerly is one of the
  most common LCP regressions on a content site.

## Images
- `next/image` only. Never a raw `<img>`.
- Give dimensions ONE of three ways: explicit width and height, a static import
  that carries them, or `fill` with a positioned parent. Never none.
- Any image that is not a fixed pixel size needs `sizes`. Without it the browser
  downloads a desktop-sized file on a phone — the most common real-world image
  defect, and it is invisible on a fast laptop.
- The largest above-the-fold image gets `priority`. Nothing else does.
- `alt` always. Decorative images get `alt=""`.

## error.tsx
An `error.tsx` file MUST be a client component — the framework requires it.
This is the one exception to the client-boundary rule above. Do not add a
comment justifying it; the filename is the justification.

# Server & Data Rules

## Every server action is a public endpoint — treat it as one
A server action is reachable over the network by anyone, without ever loading the
page that renders it. Guarding the page guards NOTHING.

Every server action does these three, in this order, before any other work:
1. authenticate — get the session; no session, return the unauthorized error
2. authorize — confirm THIS user may act on THIS specific record, by id
3. validate — parse the input with zod

Step 2 is the one that gets skipped. "The user is logged in" is not permission to
edit record 4173. Load the record, compare its owner to the session, then act.
Never trust an id, a role, a tenant, or a price that arrived from the client.

## Boundaries
- Only files in `helpers/` and `server/` may import the Prisma client.
  A `.tsx` file that imports Prisma directly is a bug — fix the import, not the rule.
- Server actions live in `helpers/actions.ts` and start with `"use server"`.
- Read paths today are Route Handlers and server components. tRPC is planned but
  NOT adopted — do not introduce it.

## Async APIs — a breaking change people still get wrong
`params`, `searchParams`, `cookies()`, `headers()` and `draftMode()` are async.
Await them. Never destructure `params` directly in the function signature, and
never read a search param synchronously.

## Return shape
- Server actions never throw to the client. They return a discriminated union:
  `{ ok: true; data: T } | { ok: false; error: string }`
  The error string is an i18n key, never a raw database message.
- Never leak an internal id, stack trace, or query in an error returned to the UI.

## Errors
- Catch narrowly. `catch (e)` that swallows everything hides real bugs.
- Log the real error on the server, return the safe key to the client.

## Performance
- Fetch in parallel with `Promise.all` when calls are independent. Sequential
  awaits that don't depend on each other are a defect.
- Select only the fields you use. No unbounded `findMany` without `take`.

## Caching and invalidation — never left implicit
- State the caching intent of every data read explicitly. Do not rely on a
  framework default: those defaults have changed between versions and are not
  something to assume.
- Every mutation ends by invalidating what it changed: `revalidatePath` for a
  known page, `revalidateTag` for a set of pages sharing the same data. A
  mutation with no invalidation is a bug, even when dev looks correct.
- Tag reads that more than one page depends on. Untagged shared data means either
  a stale page or a broad invalidation that throws away good cache.
- Do not build a custom cache layer on top of the framework's.

## Dependency direction
Components depend on typed functions exported from `helpers/`.
`helpers/` depends on the database client.
Nothing depends on a component. If you need to reverse an arrow, stop and ask.

# Database Rules

Provider is MongoDB. There are no migration files — a schema change is applied by
pushing, so the push IS the migration, and it is irreversible.

- Every model has `createdAt` and `updatedAt`.

  add a comment explaining what it cannot express.
- Soft delete over hard delete for anything a user created.
- Because the database enforces no referential integrity, deleting a document
  means handling everything that pointed at it, in the same change.

# Metadata & SEO Rules

## Every public page
Exports `generateMetadata` returning, at minimum:
- `title` — unique per page, under 60 characters
- `description` — unique per page, 140–160 characters
- `alternates.canonical` — absolute URL
- `alternates.languages` — both `ar` and `en` entries
- `openGraph` with `title`, `description`, `url`, `images`, `locale`

## metadataBase — set it once, in the root layout
Without it, every Open Graph and Twitter image URL is emitted relative and
breaks the moment a crawler or a social preview fetches it. This is the single
most common broken-preview cause. Set it from an env value, never a literal.

## Content routes — the article pattern
For a route that renders many documents from the database:
- `generateStaticParams` for the set worth prerendering. Do not prerender
  everything if the set is unbounded; prerender the known-good set and let the
  rest render on demand.
- State the revalidation intent explicitly on the segment.
- When an author publishes or edits, the publish path calls `revalidatePath` or
  `revalidateTag` for that article and for every listing it appears on. A
  published article that does not appear for an hour is a bug, not a cache.
- `notFound()` for a missing document — never an empty page, never a redirect
  to the listing. It must return a real 404 status.
- Every content route ships `not-found.tsx`.

## Structured data
- Built by a typed builder function in `helpers/`, never an inline object in JSX.
- Injected once per page. Never duplicate the same entity on one page.
- Only describe what is actually visible on the page.

## Hard rules
- Exactly one `<h1>` per page, and it matches the page's topic.
- No client-side redirect for anything a crawler should follow.
- Any page that must not be indexed sets `robots: { index: false }` explicitly.
- Adding a route means updating `sitemap.ts` in the same change.

## Async page APIs
`params` and `searchParams` are async, in `generateMetadata` and in the page
itself. Await them in both. A page that reads them synchronously is broken.

## Performance budget
- No layout shift from images: dimensions always resolvable — explicit width and
  height, a static import, or `fill` with a positioned parent.
- Every responsive image carries `sizes`. The largest above-the-fold image, and
  only that one, carries `priority`.
- Fonts loaded through `next/font`. Never a raw stylesheet link for a font.
- State the caching and revalidation intent of every public page explicitly.
- Before adding a client library, check its cost. If it ships more than ~15KB
  gzipped for one small feature, propose a native alternative first.

# Route Handler Rules

## Same security bar as a server action
A route handler is a public endpoint. Authenticate, authorize the specific
record, then validate the body with zod — in that order, before any work.
Never rely on the caller being your own frontend.

## Shape
- Return a `Response` or `NextResponse`. Never leak an error object, a stack,
  a query, or an internal id to the caller.
- Validate the body AND the search params. Both arrive from the client.
- Set the status deliberately: 400 for invalid input, 401 unauthenticated,
  403 unauthorized, 404 missing, 409 conflict. Not 200 with an error field.

## Caching
- A GET handler's caching behaviour depends on the version and on what it reads.
  Do not assume it is cached, and do not assume it is not. State the intent
  explicitly on the segment and say which you chose.
- A handler that reads cookies, headers, or the request URL is dynamic. Do not
  then mark it static and expect it to work.
- Mutating handlers never cache.

## Runtime
- Default runtime unless there is a stated reason. The edge runtime does not run
  the database client, so a handler touching the database stays on the default.
- No long-running work in a handler. If it takes seconds, it is a job, not a
  request.

## Webhooks
- Verify the signature before parsing the body. Read the raw body for that.
- Idempotent by id: the same event delivered twice must not act twice.

## Boundary with server actions
Mutations from your own UI go through server actions. Route handlers are for
what needs a URL: webhooks, third-party callbacks, feeds, files, and clients you
do not control. Do not build a parallel API for something the UI already has.

# Middleware & Project Config Rules

## Middleware runs on EVERY matching request
- Always narrow the `matcher`. Never let it run on static assets, images, or
  internal framework paths — that is wasted latency on every single request.
- No database access, no heavy computation, no third-party call. It runs before
  the response starts; whatever you add here is added to every page load.
- Session checks in middleware are a routing convenience, NOT authorization.
  The real check happens in the server action or route handler. Middleware can
  be bypassed by calling the endpoint directly.
- Locale routing lives here. Do not duplicate locale logic in pages.

## next.config
- Remote images must be allowlisted with `remotePatterns`, scoped to the exact
  host and path prefix. Never a wildcard host.
- Never disable type checking or linting during builds to make a build pass.
  If a build fails, the code is wrong.
- Any redirect that is permanent belongs here, not in a client component.

## Environment variables — one typed module
- Every env read goes through a single module that parses `process.env` with zod
  at startup and exports typed values. No `process.env.X` anywhere else.
- That module separates server values from client values explicitly. A value
  that is not prefixed for the browser must never be imported into a client
  component — the typed module is what makes that mistake impossible.
- A missing required variable fails at boot with a clear message, not at 3am
  with `undefined is not a function`.

# Building a new component

Never start by writing JSX. Follow these steps in order.

## 1. Do not build what already exists
- Grep the components folders for the noun in the task.
- Check whether shadcn/ui already ships it. If it does, install it instead of
  writing it: `pnpm dlx shadcn@latest add <component>`
- Write from scratch only when neither exists.
State which of the three paths you took, in one line.

## 2. Find the file to imitate
Open the nearest existing component of the same category and match its imports,
props style, file naming, folder position, and how it handles empty and error
states. Name that file in your first message.

## 2b. Match the route's shape
If the folder you are working in sits under a `[locale]` segment, stay inside it
and build links through the locale-aware navigation helpers. If it does not,
do not introduce one. Never hardcode `/ar` or `/en` in a path.

## 3. Decide the boundary BEFORE writing
Does this need state, an event handler, or a browser API?
- No  → server component. Do not add "use client".
- Yes → the parent stays a server component; only the interactive leaf becomes a
  client component in its own file.
Write the answer down before coding.

## 4. Contract first
Write the props type before any markup:
- only the fields the component actually renders
- no optional prop that is always passed in practice
- a union instead of two or more booleans describing one dimension
- explicit return type

## 5. Build in this order
1. static markup, with real Arabic copy from i18n keys
2. loading state — a skeleton shaped like the real content
3. empty state — an invitation to act, not a grey message
4. error state — says what happened and what to do
5. interactivity, last
A component missing steps 2–4 is not finished.

## 6. Non-negotiables before you call it done
- verified at 375px first, then desktop
- logical spacing only: ms / me / ps / pe — never ml / mr / pl / pr
- keyboard reachable with a visible focus ring
- icon-only buttons carry an aria-label from i18n
- every string is a key present in BOTH ar and en
- next/image with explicit width and height
- `pnpm exec tsc --noEmit` and `pnpm lint` pass

## 7. Report
Three lines: what you created, server or client and why, what you deliberately
left out.

# Forms

One schema. One source of truth. Validation runs twice.

## Pick the smaller tool first
- Simple form — a few fields, submits to a server action, no cross-field logic?
  Use the native React hooks: the action-state hook for the result, the
  form-status hook for the pending state, and the optimistic hook where an
  instant update helps. No form library, no extra bundle.
- Complex form — many fields, dependent validation, arrays, live feedback per
  keystroke? Then shadcn `Form` on top of react-hook-form.
Reaching for the library on a three-field form contradicts the simplicity rule
this project runs on. Say which of the two you chose and why, in one line.

## True either way
- a zod schema defined ONCE in `helpers/schemas.ts` and exported
- the SAME schema validates on the client and again inside the server action
- the form type is `z.infer<typeof schema>` — never hand-written

## Order of work
1. Write the zod schema first, with Arabic error messages taken from i18n keys.
2. Write the server action: "use server", then authenticate, authorize this
   specific record, and only then parse with the schema. Return
   `{ ok: true; data } | { ok: false; error }`. Never throw to the client.
   A server action is a public endpoint — see .claude/rules/server-data.md
3. Wire the form component. It is a client component — a legitimate case.
   Keep it a leaf: the page around it stays a server component.
4. Handle three states explicitly: idle, submitting, result.
5. On success, invalidate what changed before returning. A form that saves and
   leaves a stale list behind is not finished.

## Rules
- Client validation is convenience. The server action re-parses. No exceptions.
- Field errors render next to their field. Only form-level errors use a toast.
- The submit label is a verb and keeps the same word through the whole flow.
- Disable submit while pending. A double click must never send twice.
- After a successful mutation, revalidate the affected path — do not refetch
  by hand.
- No controlled input without a reason; react-hook-form owns the state.
- RTL: helper text, error text, and the required marker sit on the correct side.

## Done when
- submitting an empty form shows Arabic errors on the fields
- submitting with the network throttled shows a disabled pending button
- forcing the action to fail shows a readable Arabic message, never a stack trace

# Arabic / RTL audit

Arabic is the primary locale. A screen that only looks right in English is broken.

## 1. Physical properties — the main offender
Grep the changed files for:
`ml-` `mr-` `pl-` `pr-` `left-` `right-` `text-left` `text-right`
`border-l` `border-r` `rounded-l` `rounded-r`
Replace with logical equivalents:
`ms-` `me-` `ps-` `pe-` `start-` `end-` `text-start` `text-end`
`border-s` `border-e` `rounded-s` `rounded-e`
The only exception is something anchored to the viewport regardless of language.

## 2. Direction-aware icons
Must mirror: arrows, chevrons, back buttons, carousel controls, progress.
Must NOT mirror: clocks, logos, media play buttons, checkmarks, external-link.

## 3. Mixed content
- Numbers, dates, and currency go through `Intl`. Never manual formatting.
- A Latin fragment inside an Arabic sentence needs isolation, or the punctuation
  jumps to the wrong end of the line.
- Phone numbers, emails, URLs, and code render left-to-right inside an RTL line.

## 4. Sentence construction
Never concatenate translated fragments to build a sentence — Arabic word order is
not English word order. One key, with placeholders.

## 5. Typography
- Arabic needs more line height than Latin. Check descenders are not clipped.
- Arabic has no letter case: never `uppercase`, `capitalize`, or letter-spacing
  on Arabic text.
- Confirm the font actually carries Arabic glyphs at the weight you set.

## 6. Copy quality
Arabic UI copy contains no Latin words. Replace a borrowed term with a
descriptive Arabic phrase, or ask.

## Report
Every finding as file:line, the rule broken, and the fix. End with a count.

# Accessibility pass

Report every failure as file:line.

## Keyboard
- Every interactive element reachable by Tab, in visual order.
- A visible focus ring everywhere. Never `outline: none` without a replacement.
- Modals and menus trap focus while open and return it to the trigger on close.
- Escape closes any overlay.
- Nothing is reachable by hover only.

## Semantics
- Native element first: `<button>` for actions, `<a>` for navigation.
  A clickable `<div>` is a defect, not a style choice.
- One `<h1>` per page; heading levels never skip.
- Lists are real lists; tables have real `<th>` with scope.
- Icon-only controls carry an aria-label from i18n. Decorative icons are
  aria-hidden.

## Forms
- Every input has a real label tied by id. A placeholder is not a label.
- Errors are tied to their field and announced.
- Required fields are marked in text, not by colour alone.

## Colour and motion
- Text contrast 4.5:1, large text 3:1, UI borders and icons 3:1.
- No information carried by colour alone.
- Respect `prefers-reduced-motion` for anything that moves.

## Dynamic content
- Toasts and async results announced through a live region.
- Loading states announced, not only shown.
- Touch targets at least 24 by 24 css pixels to pass AA, but design for 44 —
  the larger figure is the higher level, not the AA bar. Do not report a 30px
  target as an AA failure; report it as a note.

## Report
BLOCKERS — fails AA. NOTES — passes but below best practice.

# Performance pass

Measure before changing anything. A guess is not a diagnosis.

## 1. Measure
- Run `pnpm build` and read the route table: First Load JS per route, and
  whether each route is static or dynamic. A route that became dynamic without
  anyone deciding it should is a finding on its own.
- Over ~150KB First Load JS on a public route needs a stated reason.
- To find WHAT is in the bundle, use the bundle analyzer rather than guessing
  from imports. Report the three largest entries by size.
- Identify the largest client boundary on that route.

## 2. Usual causes, in order of frequency
1. A client boundary higher in the tree than it needs to be. Push "use client"
   down to the leaf.
2. A heavy library pulled in for one small feature. Prefer a native API, or
   import only the module you need — never the whole package for one function.
3. A date, chart, icon, or editor library loaded eagerly instead of on demand.
4. Independent data calls awaited sequentially. Parallelise them.
5. An image without dimensions, or a raw `<img>`.
6. A font loaded through a stylesheet link instead of next/font, or an Arabic
   face loaded without its subset.
7. A tag manager or analytics script loading eagerly instead of after
   interactivity.
8. Remote images served without a width transformation the optimizer can read,
   or a transformation the crawler cannot resolve.

## 3. Each metric, mapped to its real cause
- LCP → the hero image, or a blocking server call above it. Prioritise the hero
  image, fetch above-the-fold data first, stream the rest.
- CLS → images and embeds without reserved space, and skeletons that do not match
  the real layout. Fix the skeleton, not the animation.
- INP → main-thread work during interaction: a long list rendered without
  virtualisation, or an expensive computation inside a handler.

## 4. Rules while fixing
- Memoization is never the first response. Find what re-renders and why.
- Do not build a caching layer. Use the framework's own primitives.
- Re-measure after each change and report the delta. A change with no measured
  improvement gets reverted.

## Report
Before and after numbers, one line per change, and anything you chose not to fix
with the reason.

# Do not guess an API. Check it.

This framework ships faster than any training data stays current. The rule is
one line: if you cannot point at a source, you do not know it.

## 1. Read the installed versions FIRST
Before any version-dependent statement, read the exact versions from
package.json: next, react, react-dom, tailwindcss, next-intl, prisma,
@prisma/client, zod. Report them in one line.
"Latest" is not a version. If package.json disagrees with your assumption,
package.json wins — every time, without argument.

## 2. Then check a source, in this order
1. `node_modules/<package>` — the installed type definitions are ground truth
   for THIS project. A signature in a .d.ts beats every blog post and every
   memory you have.
2. The official documentation for that exact major version.
3. The upgrade guide for the major you are on, when the question is
   "did this change".

## 3. Never
- Never state an API is new, deprecated, async, or renamed without a source.
- Never copy a pattern from a version other than the one installed.
- Never resolve a type error with a cast. Read the installed type and match it.
- Never write "in recent versions" or "as of the latest". Name the version, or
  say you checked and it holds for the installed one.

## 4. When you cannot verify
Say so plainly, give the option you believe is correct, and label it unverified.
An unverified answer marked unverified is useful. An unverified answer stated as
fact costs a debugging session and teaches the wrong pattern.

## 5. Record what you learn
When a check yields a durable fact — an API changed, a pattern is required in
this version, a default flipped — append ONE line to
`.claude/rules/version-notes.md`, with the version it applies to and nothing
else. That file is this project's memory of these traps. Keep it short: it
loads every session.

البساطة ومنع التكرار

هذان المبدآن هما العلاج المباشر لشكواك من الكود المعقّد والمتضخم. النموذج بطبيعته يميل للتعميم: يشوف حالة واحدة فيبني لها حلاً عاماً، ويشوف سطرين متشابهين فيستخرجهما في دالة مشتركة. النتيجة كود «نظيف» في المظهر، ومكلف في الصيانة، ومربوط ببعضه بلا سبب.

  • KISS
  • DRY
  • YAGNI
  • rule of three

البساطة

  • لا تجريد عند الاستخدام الأول. الحل العام لمستهلك واحد تكلفة صافية.
  • أقصى عمق تداخل ثلاثة مستويات. الخروج المبكر بدل التفرّع المتشعب.
  • دالة عادية أفضل من صنف. خاصية أفضل من سياق مشترك. سياق مشترك أفضل من مخزن حالة عام.
  • لا تحسين للأداء بلا قياس. التحسين الاستباقي يضيف اعتماديات خفية ويخفي أخطاء.
  • لا إعداد قابل للتهيئة لقيمة ما تغيّرت ولا مرة.
  • الحل اللي تشرحه في جملة واحدة أفضل من الحل اللي يحتاج مخططاً.

منع التكرار — بحكمة

القاعدة الشائعة «لا تكرر نفسك» تُساء قراءتها باعتبارها منعاً لتشابه النص، والصحيح إنها منع لتكرار المعرفة. شيئان متشابهان في الشكل ويتغيران لسببين مختلفين ما هما تكراراً؛ توحيدهما يخلق ارتباطاً كاذباً، وأول تعديل على أحدهما يجبرك تضيف راية شرطية للثاني، ومن هنا يبدأ التعقيد الحقيقي.

  • قاعدة الثلاثة: الاستخراج عند التكرار الثالث الحقيقي، لا الثاني.
  • اسأل قبل التوحيد: هل الاثنان يتغيران دائماً معاً؟ إذا لا، اتركهما.
  • ما يُمنع تكراره مطلقاً: الأنواع — تُشتق من مصدرها. النصوص الظاهرة — مفاتيح ترجمة. قراءة متغيرات البيئة — وحدة واحدة مصنّفة. مسارات التنقل — ملف ثوابت واحد. الأرقام السحرية — ثابت مسمّى.
  • التكرار المقصود يُوثّق بتعليق سطر واحد يشرح لماذا لم يُوحَّد.

الإعداد فوق يرفع الأرضية، لكن أكبر فرق في جودة المخرجات يجي من طريقة الطلب نفسها. أهم عادة على الإطلاق: لا تصف اللي تبيه بالكلام المجرد فقط، أشّر على ملف موجود مشابه وقل «اتبع هذا النمط». النموذج يقلّد نمطاً حاضراً في سياقه أفضل بكثير مما ينفّذ وصفاً نظرياً — وهذي وحدها تحل أغلب مشكلة العشوائية.

قبل البدءجلسة نظيفة لكل مهمة مستقلة. السياق المتراكم من مهمة سابقة يشوّش على اللاحقة أكثر مما يفيدها.
التخطيطشغّل أمر التخطيط، واقرأ الخطة سطراً سطراً. تصحيح خطة من عشرة أسطر أرخص بكثير من تصحيح مئتي سطر كود.
أثناء التنفيذراقب أول ملف يكتبه. إذا انحرف النمط من البداية، أوقفه فوراً بدل ما تنتظر النهاية — الانحراف يتراكم ولا يصحح نفسه.
عند الانحراف المتكررإذا صححت له نفس الشي مرتين، المشكلة مو فيه بل في ملف التعليمات. أضف القاعدة مكتوبة بصيغة قابلة للتحقق. وإذا تكررت رغم الكتابة، ارفعها من التعليمات إلى الخطافات.
قبل الاعتمادشغّل أمر المراجعة. اقرأ المخرجات بنفسك؛ الوكيل يكشف المخالفات لكن الحكم النهائي لك.
الجلسات الطويلةراقب امتلاء السياق. لما يقارب الامتلاء، إما تضغطه أو — الأفضل — تنهي المهمة وتبدأ جلسة جديدة.

قائمة التحقق النهائية

بعد ما ينفّذ النموذج الإعداد، امش على هذي القائمة مرة واحدة. أغلب حالات «الإعداد ما اشتغل» سببها ملف ما تحمّل أصلاً، وليس قاعدة مكتوبة غلط.

  • ملف التعليمات الرئيسي يظهر ضمن ملفات الذاكرة عند فحص السياق داخل الجلسة.
  • ملفات القواعد الخمسة موجودة، وكل واحد منها فيه ترويسة مسارات صحيحة.
  • الخطاف السريع يشتغل: اطلب تعديلاً بسيطاً وشوف هل التنسيق تغيّر تلقائياً، وهل رجع الرد بسرعة بلا توقف محسوس.
  • الخطاف الشامل يمنع: أدخل خطأ نوع متعمداً واترك النموذج «يخلّص»، وتأكد إنه أُجبر على الرجوع والتصحيح.
  • قائمة المنع فعّالة: اطلب منه يقرأ ملف البيئة وتأكد إنه رُفض.
  • الوكيلان الفرعيان يظهران في قائمة الوكلاء المتاحة.
  • المهارات الخمس تظهر في قائمة المهارات، ومهارة البناء تشتغل تلقائياً عند طلب مكوّن جديد.
  • حدود المسارات فعّالة: استورد من مسار إلى مسار عمداً وتأكد إن التنبيه وصل للنموذج، لا إنه ظهر في المحرر فقط.
  • لا توجد قاعدة مكتوبة في مكانين: ابحث عن أي بند تكرر بين الملف الرئيسي وملفات القواعد واحذف أحدهما.
  • الخطافان يشتغلان بلا صدفة نظام: افتح ملف الإعدادات وتأكد إن الأمر يستدعي بيئة التشغيل فقط.
  • الفحص على الخادم يمنع فعلاً: ادفع فرعاً فيه تنبيه حدود وتأكد إنه فشل هناك رغم نجاحه محلياً.
  • حساسية الحروف ممسوكة: غيّر حالة حرف في اسم ملف مستورد وتأكد إن الفحص على لينكس سقط.
  • ما فيه سر في متغيّر ببادئة النشر العام: افحص ملف البيئة سطراً سطراً مرة واحدة.
  • لمشروع قائم: خط الأساس مُلتقط، والتقاطه مرتين متتاليتين يعطي نفس النتيجة.
  • لمشروع قائم: إنشاء الإعدادات ما حرّك ولا ملف مصدر واحد.
  • مهارة التحقق تشتغل: اسأل عن سلوك واجهة برمجية وتأكد إن أول ما يفعله النموذج قراءة الإصدارات المثبّتة.
  • ملف الملاحظات ما فيه سطر بلا رقم إصدار.
  • الأمران المختصران يشتغلان بالشرطة المائلة.
  • الملفات المحلية مضافة إلى قائمة الاستثناء من المستودع.
  • سطر المكدّس يطابق الواقع: لا ذكر لأداة مخططة كأنها مستعملة.
  • إجراء خادم واحد على الأقل يفحص الهوية والصلاحية قبل التحقق من المدخلات.
  • الملف الرئيسي تحت مئتين سطر، وما فيه بندان متناقضان.
  • لحظة المنع صحيحة: خطّاف ما بعد التعديل يُبلِّغ فقط، والبوّابة في لحظة التوقّف وفي الفحص على الخادم.
  • لا قاعدة مكرّرة بين التعليمات والقواعد المشروطة والمهارة والذاكرة التلقائية — المواضع أربعة لا ثلاثة.
الترتيب المُوصى به للتنفيذابدأ بالخطافات والصلاحيات — عائدها فوري ومضمون لأنها لا تعتمد على اقتناع النموذج. بعدها اضبط قسم انضباط النطاق في الملف الرئيسي، فهو المسؤول عن التضخم والتعقيد. القواعد المشروطة تجي لاحقاً لما يكبر الملف الرئيسي. الوكلاء الفرعيون آخر شي، لما تصير جلساتك طويلة فعلاً.
