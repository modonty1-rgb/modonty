# Workflow موحّد — أي تطبيق موبايل

## الغرض

هذا هو تسلسل العمل الملزم لأي تطبيق موبايل في Modonty. يمنع التخمين، تكرار الصور، والتنفيذ قبل اكتمال العقد البصري والوظيفي.

القواعد الحاكمة للشكل والهندسة لا تُكرّر هنا: `UIUX-RULES.md` ثم `ENGINEERING-RULES.md` هما الحاكمان عند التعارض.

## 0. قبل البدء

### قاعدة ذهبية — الملف يحكم، لا الذاكرة

1. **المصدر الدائم للحقيقة هو ملفات المشروع الموجودة على الجهاز.** لا تعتمد أي ذاكرة وكيل، أو ملخص محادثة، أو ادعاء سابق بديلاً عن قراءة الملف الحالي.
2. قبل أي تعديل أو إعداد أو تبعية أو قرار قابل للتكرار: اقرأ الملف المرجعي الحالي، ثم نفّذ التغيير، ثم ثبّت النتيجة في ملف مرجعي داخل المشروع.
3. كل تغيير يخص المشروع — إعداد، تبعية، بناء، متغير بيئة غير حساس، قرار معماري، أو حالة تشغيل — يُسجّل فورًا في الوثيقة المناسبة مع الدليل (أمر/ملف/سطر). لا توجد «خطوة عابرة» غير موثقة.
4. هذه بوابة عمل إلزامية (Hook): إن لم يوجد ملف مرجعي أو تعارضت الذاكرة معه، يتوقف التنفيذ حتى تُقرأ الحالة الفعلية ويُسجَّل القرار.
5. **التسليم بين الوكلاء إلزامي:** يجب أن يفهم أي وكيل آخر (كوديكس أو كلود) من الملفات المحلية وحدها: أين توقف العمل، ما الذي تغيّر، ما الدليل، ما الحاجز، وما الفعل التالي الواحد. لا يُسمح بتوثيق يفترض قراءة المحادثة أو ذاكرة وكيل سابق.

1. اقرأ `UIUX-RULES.md` و`ENGINEERING-RULES.md` كاملين قبل أي سطر كود.
2. اقرأ اتفاق العمل، سجل الجلسة، ووثائق نطاق التطبيق إن وجدت.
3. افحص الكود والـschema وعقود API الفعلية للسطح المطلوب. لا تعتمد على الذاكرة أو mock data.
4. تحقّق من المصدر الرسمي الحالي للمكتبة أو المنصة عند أي قرار تقني أو UX قابل للتغير.
5. إن ظهر تعارض بين الطلب والواقع التقني أو UX، يُقال قبل التصميم مع الدليل والبديل؛ لا يُخفى حتى ما بعد الاعتماد.

## 1. تنظيم الأصول — قبل أول صورة

داخل المشروع فقط، أنشئ أو استعمل هذا الهيكل المسطّح:

```text
documents/design/assets/<app>/
├─ approved/     # المعتمد فقط
├─ in-review/    # المراجعة الحالية فقط
├─ rejected/     # الملغي أو التجريبي القديم فقط
└─ README.md      # المعنى والحالة الحالية للمجلدات
```

- لا مجلدات إصدارات داخل `approved` أو `in-review`.
- لا نسخة ثانية للشاشة في مجلدين نشطين.
- عند الاعتماد تُنقل الصورة من `in-review/` إلى `approved/` بالاسم الثابت نفسه.
- الصورة القديمة أو التجريبية تخرج من مسار العمل النشط إلى `rejected/`؛ لا تحذفها إلا بطلب صريح.
- لوحة الفهرسة `SCREEN-SCAN.png` تبقى في `in-review/` ما دامت تضم شاشات قيد المراجعة؛ ليست صورة اعتماد.

## 2. النطاق والبيانات

1. حدّد فعل العميل، الحقول الفعلية من API، والـendpoint الذي تخدمه الشاشة.
2. استخدم بيانات عربية واقعية من بيئة التطوير فقط؛ الحقل الغائب يُحذف ولا يُخترع.
3. حدّد الحالات الأربع قبل التصميم: تحميل هيكلي، فارغ بسبب وفعل واحد، خطأ باسم المشكلة وإعادة محاولة، وبلا شبكة مستقلة.
4. لكل فعل كتابة، حدّد التأكيد المطلوب وتغيّر الصف في قاعدة التطوير الذي يثبت نجاحه.

## 3. ترقيم ومسار الشاشات

1. `S00` للمعايير والهوية، `S01` للدخول، `S02` للرئيسية إن وجدت.
2. يبدأ ما بعدها من `S03` وفق رحلة العميل من أعلى الصفحة إلى أسفلها، ثم الأسطح التابعة لكل انتقال. لا يُرتّب حسب وقت رسم الملفات أو اسم التبويب فقط.
3. يُكتب جدول دائم: المعرف، اسم السطح، ومن أي عنصر يصل العميل إليه.
4. في صورة المراجعة فقط، يوضع وسم `Sxx` أحمر صغير بجانب كل انتقال من الرئيسية يبيّن وجهته. الوسم مرجع للفريق وليس UI منتجاً، ويُزال قبل الإنتاج.
5. خالد يراجع ويشير إلى الشاشة بالمعرف فقط؛ لا أسماء مبهمة ولا أرقام متغيرة.

## 4. محاكاة قابلة للقرار

1. خذ دقة جهاز الاختبار وكثافته الحقيقيتين قبل الرسم.
2. ارسم شاشة كاملة بالحجم الفعلي، مع شريطي النظام وsafe areas؛ لا لقطة مقصوصة ولا لوحة مصغرات لاتخاذ قرار.
3. طبّق قيم `dp` بعد تحويلها بكثافة الجهاز. مثال جهاز كثافته `2×`: هدف `48dp` يرسم `96px`.
4. لوحة `SCREEN-SCAN.png` للفهرسة والانتقال السريع فقط؛ ملف `Sxx-*.png` الكامل هو مادة الاعتماد.
5. لا تعدّل التطبيق أثناء مرحلة الصورة.

### تفويض تصميم صفحة كاملة

عندما يقول خالد إن الشاشة «عليك»، يبني المصمم **التصور الكامل** وفق القواعد الأساسية:

1. الهرمية، safe areas، أهداف اللمس، RTL، tokens، ومكوّنات النمط المعتمد تُطبّق من أول صورة.
2. تعرض المحاكاة المسار الكامل: البيانات، الأفعال، التأكيدات، الحالات والنتيجة المتوقعة؛ لا بطاقة معلومات ناقصة بسبب أن API لم يُبنَ بعد.
3. يجوز استعمال بيانات عربية تجريبية واقعية داخل **صورة المراجعة فقط** كي يكون القرار البصري كاملاً. تُعلّم بأنها بيانات تصميم، ولا تدخل التطبيق أو API أو قاعدة البيانات.
4. بعد اعتماد الصورة، تُستخرج كل خانة وفعل إلى عقد بيانات صريح. ما لا تدعمه البيانات الفعلية يُنفّذ لاحقاً أو يحجز صراحة؛ لا يتحول إلى نص أو رابط وهمي في التطبيق.

## 5. مراجعة واعتماد الصورة

1. نعمل شاشة واحدة فقط في كل مرة.
2. عند تعديل الصورة قبل الاعتماد، يُستبدل الملف نفسه في `in-review/`؛ لا نسخ `v2` أو صور موازية.
3. لا يقال «معتمدة» إلا بعد تأكيد خالد الصريح.
4. بعد التأكيد: انقل الملف إلى `approved/`، حدّث `SCREEN-STATUS.md` والـqueue، وجدّد لوحة الفهرسة.
5. الصورة المعتمدة عقد بصري 100%؛ أي تغيير مرئي لاحق يعيدها للمراجعة قبل تعديل الكود.

## 6. بوابة التنفيذ

لا يبدأ كود واجهة شاشة إلا بعد توفر الأربعة:

1. الصورة في `approved/`.
2. نطاق البيانات وعقد API الفعلي.
3. قرار موثق لأي اختلاف تقني أو UX محتمل.
4. مكوّنات tokens/الأيقونات/التنقل اللازمة معتمدة أو موجودة.

## 7. التنفيذ

1. ابنِ من الصورة المعتمدة ومن `theme/tokens` والمكوّنات المشتركة فقط؛ لا hex أو مسافة أو نمط داخل ملف الشاشة.
2. استعمل `ModontyIcon`، و`expo-image`، وnative stack/native tabs كما تحكم القواعد.
3. القوائم الطويلة: FlashList + عنصر `memo` + مراجع دوال ثابتة + لا كائن نمط داخل الرسم.
4. كل شاشة تحمل بياناتها الدنيا فقط؛ لا prefetch ولا cache لتفاصيل صفحة أخرى.
5. اقرأ `response.ok` قبل `response.json()`، ولا `catch {}` صامت.
6. لا تغيير جانبي في شاشة أو مكوّن خارج نطاق الصورة المعتمدة.

## 8. الاختبار الوظيفي

1. اختبر كل endpoint مرتبط بالشاشة: نجاح، بلا صلاحية، مدخل خطأ، وبلا شبكة.
2. اختبر الحالات الأربع على الشاشة نفسها.
3. لفعل الكتابة: سجّل حالة الصف قبل وبعد في قاعدة التطوير، وكود HTTP والناتج الخام.
4. لا تلمس قاعدة الإنتاج. قبل أي أمر قاعدة بيانات، تحقّق أن `DATABASE_URL` الفعّال هو بيئة التطوير.

## 9. المطابقة على جهاز فعلي

1. شغّل Metro واحداً فقط مع `expo start --clear` عند الحاجة.
2. افحص الجهاز بـ`adb devices -l` وافتحه بـ`scrcpy` بلا Android Studio.
3. التقط لقطة Android فعلية بالبيانات نفسها المستخدمة في صورة الاعتماد.
4. قارنها بـoverlay/diff مع الصورة المعتمدة.
5. أي اختلاف مرئي أو وظيفي = راسب؛ أصلحه ثم أعد اللقطة. لا تعرضه لخالد كمنتهٍ قبله.

## 10. التسليم

لا تقل «تم» بلا دليل. تقرير التسليم يذكر:

- مسار صورة الاعتماد ولقطة الجهاز.
- ناتج `tsc` بعدد الأخطاء.
- البناء أو التشغيل الذي نُفّذ فعلاً.
- الحالات والـendpoints المختبرة وما لم يختبر صراحة.
- ملف وسطر لكل تغيير مهم.

## 11. قبل الإنتاج

1. أزل كل وسم مرجعي أحمر `Sxx` وكل annotation خاص بالمراجعة.
2. تأكد أن الصور النهائية لا تحوي أرقاماً أو بيانات تجريبية لا تظهر للمستخدم.
3. أعد بوابة الاختبار كاملة ولقطة الجهاز الفعلي قبل الإصدار.
