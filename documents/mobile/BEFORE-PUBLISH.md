# قبل النشر — التواصل مع عملاء تطبيق Modonty

هذه وثيقة تحضير، وليست إذناً للنشر أو لإرسال أي رسالة إلى عميل حقيقي.

## القرار

يوجد مركز واحد في الأدمين باسم **التواصل مع العملاء**. الرسالة المحفوظة داخل التطبيق
هي مصدر الحقيقة؛ إشعار النظام Push تذكير اختياري يفتح الرسالة نفسها، ولا يحمل قراراً
مالياً أو استحقاقاً بحد ذاته.

## ما نريد إرساله

| الحالة | المصدر الذي يغيّر الحقيقة | ما يراه العميل |
|---|---|---|
| خبر أو خدمة جديدة | حملة رسالة داخل التطبيق | رسالة + Push اختياري يفتحها |
| هدية أو اشتراك مجاني | خدمة الاستحقاقات على الخادم أولاً | تأكيد مرتبط بتفاصيل الاشتراك |
| عرض أو ريفيرال | حملة مع شريحة مستهدفة ورابط داخلي | رسالة + Push يفتح صفحة العرض/الإحالة |
| تحديث JavaScript متوافق | EAS Update تدريجي | تحديث التطبيق، لا حملة تسويقية |
| تحديث Native إلزامي | إصدار جديد + حد أدنى للإصدار | تنبيه واضح للتحديث عند فتح التطبيق |

لا نعالج التحديث البرمجي بإشعار تسويقي، ولا نعالج هدية أو باقة ببيانات Push. الخادم
هو الذي يغيّر حالة الاشتراك، ثم تظهر الرسالة كنتيجة لذلك.

## دورة الحملة في الأدمين

1. ينشئ موظف مخول مسودة: العنوان، النص، الوجهة الداخلية، ونوع الحملة.
2. يختار الجمهور: جميع العملاء النشطين، أو باقة، أو بلد، أو لغة، أو شريحة محددة.
3. يرى معاينة عربية على الهاتف ويرسل اختباراً إلى حساب داخلي فقط.
4. يراجع موظف ثانٍ الحملة ثم يجدولها أو يرسلها.
5. ينشئ الخادم رسالة داخل التطبيق لكل مستلم مستهدف، ثم يرسل Push إلى أجهزته المسجلة
   ذات الإذن فقط.
6. تسجل النتائج: مستهدف، أنشئت الرسالة، طلب Push، إيصال Push، فتح الرسالة، والنقر على
   الوجهة. فشل Push لا يلغي الرسالة داخل التطبيق.

## الأجهزة والإذن

- لا يعني تنزيل التطبيق أن صاحبه عميل معروف. الربط الصحيح يبدأ بعد تسجيل الدخول.
- بعد موافقة المستخدم على إذن الإشعارات، يسجل التطبيق الجهاز وExpo Push Token وربطه
  بحساب العميل عبر `devices/register`.
- لا تخزن بيانات حساسة في Payload الإشعار.
- فتح الإشعار يمرر `messageId` ووجهة داخلية فقط، ثم تجلب الشاشة البيانات الحديثة من
  الخادم.

## ما هو موجود الآن — فحص 2026-08-28

- `MobileDevice` موجود في `shared/prisma/schema/schema.prisma` ويخزن `clientId` وExpo
  token والمنصة واسم الجهاز والإصدار وحالة التفعيل وآخر ظهور. لا يخزن native token أو
  حالة إذن الإشعارات بعد؛ هذان توسعان مقترحان لا حقيقة حالية.
- `POST /api/mobile/v1/devices/register` يربط Expo token بحساب العميل بعد التوثيق، ويعيد
  تفعيل الجهاز عند إعادة التسجيل: `console/app/api/mobile/v1/devices/register/route.ts`.
- `sendPushToClient` يرسل للأجهزة المفعلة لعميل واحد ويعطل token الذي يرجع له Expo
  بالخطأ `DeviceNotRegistered`: `console/lib/mobile-api/push.ts`.
- لا يوجد في السكيمة الآن نموذج حملة جماعية، أو Inbox للعميل، أو Referral. نموذج
  `ClientNotification` الحالي موجه لفريق المحتوى عبر Telegram وليس رسائل العميل داخل
  التطبيق.
- ملاحظة محجوزة للإصلاح بقرار منفصل: `console/lib/mobile-api/push.ts` يحتوي `catch {}`
  صامتاً، وهو مخالف لـ`ENGINEERING-RULES.md`. لم يُعدّل ضمن مهمة التوثيق.

## عقد بيانات مقترح قبل التنفيذ

### Campaign

- الحالة: مسودة، بانتظار المراجعة، مجدولة، مرسلة، ملغاة.
- النوع: خبر، عرض، إحالة، استحقاق، تشغيلي.
- الجمهور: قاعدة اختيار قابلة للتدقيق، لا قائمة مخفية داخل الواجهة.
- المحتوى: عنوان، نص، وجهة داخلية اختيارية من عقد API.
- التدقيق: المنشئ، المراجع، وقت الجدولة، وقت الإرسال، وعدد المستهدفين.

### In-app message

- معرف الحملة، حساب العميل، العنوان والنص والوجهة، وقت الإنشاء، وقت القراءة، ووقت الفتح.
- تبقى الرسالة قابلة للقراءة حتى لو لم يصل Push أو أغلقه المستخدم.

### Device registration

- حساب العميل، نوع الجهاز، المنصة، Expo token، native token، حالة إذن الإشعارات، وآخر
  ظهور. الحقول الثلاثة الأخيرة توسع مستقبلي؛ الموجود الآن موثق في القسم السابق.
- token واحد لا يمنح حق الوصول؛ التوثيق على الخادم يحدد الحساب قبل الحفظ أو الإرسال.

### Referral

- رمز إحالة فريد، مالكه، القواعد، تاريخ الانتهاء إن وجد، التسجيل المنسوب إليه، والاستحقاق
  الناتج بعد تحقق الخادم.
- لا تحسب المكافأة في التطبيق، ولا يكفي فتح الرابط لاستحقاقها.

## بيانات التجربة قبل التنفيذ

كل تجربة كتابة تقع حصراً في `modonty_dev`. يمنع لمس `modonty` الإنتاجية.

| ما نجهزه | الغرض | التحقق المطلوب |
|---|---|---|
| حساب اختبار قائم مثل Kimazone | تسجيل الدخول وربط جهاز | لا نغيّر كلمة المرور أو بيانات عميل خارج التجربة |
| جهاز اختبار مربوط | اختبار التسجيل، الإذن، وفتح Push | صف الجهاز قبل/بعد في `modonty_dev` |
| حملة مسودة داخلية | المعاينة والإرسال التجريبي | لا جمهور حقيقي ولا إرسال جماعي |
| رسالة داخل التطبيق تجريبية | قائمة الرسائل وDeep link | فتح الرسالة والوجهة من جهاز فعلي |
| استحقاق تجريبي محدود | هدية/اشتراك مجاني | تغير صف الاستحقاق قبل/بعد، ثم عكسه بسجل واضح |
| رمز إحالة تجريبي | إسناد الإحالة ومنع التكرار | تجربة ناجحة ومكررة ومرفوضة |

اختبار Push الحقيقي على Android يتطلب development build؛ Expo Go لا يدعم Push remote
لهذا التطبيق. لا نسجل token شكلياً لمجرد ملء البيانات، لأن ذلك لا يثبت وصولاً أو فتحاً.

## الحملة التجريبية الأولى — الإحالة

**الحالة:** مسودة؛ لا ترسل ولا تظهر في التطبيق قبل وجود إحالة قابلة للتحقق على الخادم.

| الحقل | القيمة المعتمدة للمسودة |
|---|---|
| النوع | إحالة |
| العنوان | رشّح مدونتي واحصل على شهر مجاناً |
| النص | عندما ينضم عميل جديد إلى مدونتي عن طريقك، نضيف لك شهراً مجانياً إلى اشتراكك. |
| الاستحقاق | شهر واحد مجاني للعميل المُحيل بعد تحقق الخادم من الإحالة |
| الجمهور التجريبي | حساب Kimazone فقط |
| Push | يفتح الرسالة داخل التطبيق، لا ينفذ الاستحقاق مباشرة |

ما زال قرار **طريقة إثبات «عن طريقك»** مطلوباً قبل التنفيذ: رابط إحالة فريد، أو رمز
إحالة فريد، أو إدخال يدوي موثق من الموظف. لا يصح أن نرسل الحملة أو نعد بشهر مجاني قبل
حسم هذه الآلية؛ فلا يمكن للخادم منح الاستحقاق بعدل أو منع التكرار من دونها.

### معيار واجهة رسالة الإحالة

- يظهر Hook الحملة النشطة في الرئيسية كسطر تنقّل كامل الضغط، ثم يفتح شاشة تفاصيل عبر
  native stack. التنبيه لاحقاً يفتح الوجهة نفسها كتذكير، وليس مدخل الميزة الوحيد.
- Hook الإحالة يسبق ملخص الاشتراك، ويستعمل طبقة `warning` بنسبة 12% فوق
  `surfaceRaised` وحداً كاملاً من `warning`. النص أبيض والسهم كهرماني؛ في التنفيذ
  يضاف هذا كـ`warningSurface` token قبل استعماله في أي شاشة.
- سطح التفاصيل يستهلك الحقول الموجودة فقط: `type` و`title` و`body`؛ لا يظهر زر أو رابط
  عند غياب `action` حقيقي في عقد API.
- آلية الإحالة المعتمدة للتصميم: يرسل المرشّح رقم جوال العميل بعد تأكيد أنه شرح له الخدمة
  وأن العميل وافق على التواصل. يتواصل فريق مدونتي مع العميل؛ عند اشتراكه وسداد الدفعة يمنح
  الخادم المرشّح شهراً مجانياً تلقائياً.
- CTA الأساسي الوحيد: «إرسال بيانات العميل». يفتح تأكيداً قبل الحفظ، ولا يمنح المكافأة.
- يلزم `ReferralLead` صريح: رقم العميل، معرف المرشّح، تأكيد المرشّح، حالة التواصل، حالة
  الاشتراك والسداد، والاستحقاق وسجل تدقيق idempotent.
- رقم الجوال بيانات شخصية تُجمع من غير صاحبها. تأكيد المرشّح ليس بديلاً عن إبلاغ العميل
  المرشّح وأخذ موافقته مباشرة عند التواصل. تجمع الشاشة الحد الأدنى (رقم واحد فقط) وتوضح
  غرضه. المرجع: [نظام حماية البيانات الشخصية لدى SDAIA](https://dgp.sdaia.gov.sa/wps/portal/pdp/knowledgecenter/details/PDPL2).
- تحتاج الرئيسية عقداً صغيراً مستقلاً باسم `activeCampaignHook` يحوي معرف الحملة والعنوان
  والوجهة فقط. عند غيابه تخفي الرئيسية البار كاملاً؛ لا تحمل تفاصيل الإحالة مسبقاً.
- المرجع المرئي لهذه المرحلة: `S03-referral-message.png` داخل لوحة `SCREEN-SCAN.png`.

قبل كل أمر يمس القاعدة نشغّل فحص `DATABASE_URL` الموثق في قواعد الجلسة. إذا ظهر
`modonty` بلا `_dev` في سطر فعّال نتوقف ولا نكمل. الأوامر التالية ممنوعة: `prisma db push`،
`prisma migrate`، و`deleteMany({})` بلا شرط.

**نتيجة فحص 2026-08-28:** `shared/.env:4` و`shared/.env.local:1` يعرّفان
`DATABASE_URL` الفعّال على `modonty_dev`. يوجد رابط إنتاج تحت اسم متغير آخر في
`shared/.env.local`؛ لا يقرأه كود المستودع ولا ينسخ إلى أي سكربت.

## مراحل التنفيذ بعد اعتماد التصميم

1. مراجعة السكيمة الحالية و`devices/register` وعقود API؛ لا نبني حقولاً موازية قبل ذلك.
2. تسجيل الجهاز والإذن وInbox داخل التطبيق.
3. حملات الأدمين: مسودة، جمهور، معاينة، اختبار، مراجعة، وجدولة.
4. إرسال Expo Push مع receipts ومعالجة token غير الصالح.
5. هدية/استحقاق وإحالة بخدمات خادم idempotent وسجل تدقيق.
6. تحديثات EAS عبر قناة اختبار ثم rollout تدريجي؛ أي تحديث Native يحتاج build جديداً.
7. اختبار كامل على جهاز Android فعلي: وصول الرسالة في المقدمة والخلفية، فتحها، عدم وجود
   اتصال، إذن مرفوض، token منتهي، وبيانات الاستحقاق قبل/بعد.
