# اقتراح النسخة الأولى — Modonty Console Mobile

## الأساس الذي اتفقنا عليه

التطبيق ليس نسخة من Console الويب، ولا تطبيق حجوزات في المقام الأول.

**هو تطبيق إشعارات ومتابعة عمل العميل.**  
اليوم أغلب الأحداث تصل إلى Telegram، بينما العميل العربي غالبًا لا يستخدمه. تطبيق الموبايل يجعل الإشعار يصل للعميل، ثم يفتح له الإجراء الصحيح فورًا.

---

## قرار البدء السريع

| نبدأ الآن | لا نحتاجه الآن | قرارنا |
|---|---|---|
| Login + التحديثات + مراجعة المقال | Android Studio على جهازك | نبدأ بـDummy Data ونراجع من هاتفك |
| Push حقيقي بعد اعتماد الواجهات | ربط API أو حذف Telegram | نربطه في المرحلة التالية فقط |
| تجربة Android من هاتفك | جهاز تطوير قوي لديك | بناء سحابي عبر Expo عند الحاجة |

---

## كيف نعمل ونجرب بدون Android Studio

أنت لا تحتاج تثبيت Android Studio ولا تشغيل أي محاكي على جهازك.

```text
أنا أبني واجهة Expo
        ↓
أنت تراجعها على هاتفك بـ Expo Go عبر QR
        ↓
نتفق على الـUI والـDummy Data
        ↓
أبني نسخة اختبار سحابية (Development Build)
        ↓
تثبتها من رابط/QR وتجرب Push الحقيقي
```

| المرحلة | ما تستخدمه أنت | ما نتحقق منه |
|---|---|---|
| تصميم الواجهات | Expo Go على الجوال | التنقل، النص، الأزرار، والـDummy Data |
| Push حقيقي | نسخة اختبار من رابط/QR | استقبال الإشعار وفتح العنصر الصحيح |
| الإطلاق | Google Play / App Store | فقط عند جاهزية النسخة الأولى |

- Expo Go مجاني وخفيف؛ نستخدمه لمراجعة الواجهة فقط.
- Push الحقيقي يحتاج Development Build سحابيًا، وليس Android Studio على جهازك.
- EAS Build ينشئ نسخة Android في السحابة؛ نحن لا نحتاج محاكيًا محليًا.
- نتابع القرار من هذا الـHTML، ثم من هاتفك عبر لقطات الشاشة وملاحظاتك.

## دورة العمل الأساسية

```text
فريق المحتوى يجهز المقال
        ↓
يُرسل للعميل للمراجعة
        ↓
العميل يفتح الإشعار
        ↓
يعتمد المقال أو يطلب تعديلًا
        ↓
فريق المحتوى يستلم القرار ويكمل العمل
```

هذه هي أول رحلة نصممها ونثبتها.

## ما يدخل النسخة الأولى

### 0. الدخول والجلسة

- شاشة دخول واضحة: **username أو البريد الإلكتروني** + كلمة المرور.
- إظهار/إخفاء كلمة المرور، رسالة خطأ مفهومة، و«نسيت كلمة المرور؟».
- بعد الدخول تبقى الجلسة آمنة؛ العميل لا يعيد كتابة البيانات كل مرة يفتح التطبيق.
- logout من «حسابي» فقط.

### 1. مركز الإشعارات — قلب التطبيق

- كل حدث مُفعّل للعميل يصل أولًا إلى سجل دائم داخل التطبيق، ثم يُرسل له Push حسب تفضيله وأولوية الحدث.
- الضغط على الإشعار يفتح العنصر الصحيح، لا مجرد الصفحة الرئيسية.
- تبويب «التحديثات» يحتفظ بتاريخ الأحداث وحالتها: جديد / تمت رؤيته / تم الإجراء.
- أحداث المقال والتفاعل الحالية موجودة بالفعل في الكونسل عبر Telegram؛ نستخدم نفس مفاتيح الأحداث كمرجع واحد، لا نبني قائمة موازية للموبايل.

### تصور الإشعارات: ما سنستخدمه

```text
حدث في الكونسل
      ↓
سجل إشعار دائم للعميل (In-app inbox)
      ├── Push للموبايل عبر Expo Notifications
      └── Telegram يستمر بالتوازي في البداية
```

- **Expo Notifications + Expo Push Service** للنسخة الأولى: التطبيق يستقبل Push أصليًا على iOS وAndroid، والسيرفر يرسله من الخلفية.
- خدمة إرسال الـPush من Expo **مجانية**؛ التكلفة المحتملة لاحقًا تكون من بناء التطبيق/تحديثاته السحابية أو حسابات المتاجر، لا من عدد رسائل الـPush نفسها.
- **In-app inbox** هو المصدر الموثوق: إن كان الهاتف بلا إنترنت أو أُغلق الـPush، يبقى الحدث ظاهرًا داخل «التحديثات» حتى يُرى أو يُنجز.
- **Telegram لا نحذفه الآن**: يبقى قناة موازية خلال الانتقال؛ لا نكسر تنبيهات العملاء الحالية.
- لكل إشعار: نوع الحدث، العنصر المرتبط، الوقت، الحالة، ورابط عميق يفتح المقال أو السؤال أو الرفع الصحيح.
- نطلب إذن Push بعد تسجيل الدخول وعند شرح فائدته، وليس قبل أن يعرف العميل لماذا يحتاجه.

### قاعدة الـevents

كل الـevents المفعّلة تظهر في سجل التطبيق. أما تنبيه الـPush فيُضبط من «حسابي» بحسب الفئة؛ الافتراضي يركز على ما يحتاج إجراءً، حتى لا يتحول الهاتف إلى ضوضاء بسبب المشاهدات والإعجابات.

| الفئة | أمثلة | الافتراضي |
|---|---|---|
| يحتاج إجراء | مقال للمراجعة، سؤال مباشر، تعليق/رسالة جديدة، فشل رفع | Push فوري + يظهر في التحديثات |
| متابعة عمل | تعديل مكتمل، معالجة Reel/Video، اعتماد أو رفض | Push + يظهر في التحديثات |
| نشاط ومؤشرات | مشاهدة، إعجاب، حفظ، مشاركة، زيارة | يظهر في التحديثات؛ Push اختياري/ملخص |

لا نعتمد «22 event» كتخمين: الكود الحالي يحوي كتالوجًا لزوار المقال والصفحة والتواصل المباشر، وأول خطوة تنفيذية ستكون تدقيقه وربط أحداث مراجعة المقال ورفع المحتوى به في catalog واحد محايد عن Telegram.

### 2. مراجعة المقال

- مقالات بانتظار المراجعة.
- معاينة المقال بشكل قراءة مريح على الجوال.
- **اعتماد** المقال.
- **طلب تعديل** مع ملاحظة واضحة للـcontent team.
- متابعة الحالة: قيد المراجعة / يحتاج قرارك / تم التعديل / منشور.

### 3. الرسائل والتفاعل

- أسئلة الزوار: يقرأ العميل السؤال ويرد.
- ملاحظات وتعليقات العملاء: يقرأ، يرد، أو يعتمد/يرفض عند الحاجة.
- المتابعون/المشتركون: يرى من تابع نشاطه والتنبيه عند وصول متابعة جديدة.

### 4. رفع المحتوى المرئي

- رفع Reel.
- رفع Video.
- يرى حالة الرفع أو المعالجة أو المراجعة.
- لا نبني Media Manager كامل في البداية؛ فقط رحلة رفع واضحة وموثوقة.

### 5. حسابي وإعدادات الإشعارات

- بيانات العميل المختصرة.
- تشغيل/إيقاف فئات التنبيه غير الحرجة.
- دعم ومساعدة.
- فتح Console Web عند الحاجة لأداة غير موجودة في التطبيق.

## التنقل المقترح للنسخة الأولى

```text
[ التحديثات ]  [ المقالات ]  [ التفاعل ]  [ رفع ]  [ حسابي ]
```

| التبويب | وظيفته |
|---|---|
| التحديثات | كل ما حدث ويحتاج انتباهًا؛ هو الصفحة الأولى |
| المقالات | مراجعة، اعتماد، طلب تعديل، ومتابعة الحالة |
| التفاعل | أسئلة، ملاحظات، تعليقات، ومتابعون |
| رفع | Reel أو Video وحالة كل عملية رفع |
| حسابي | إعدادات التنبيهات والمساعدة وفتح الويب |

**الحجوزات والـLeads تبقى خارج أول UI** إلا إذا قررنا لاحقًا أنها event حرِجة ضمن مركز التحديثات.

## شكل صفحة «التحديثات»

```text
مرحبًا، [اسم العميل]

جديد لك اليوم

🔴 مقال ينتظر موافقتك                    [ مراجعة ]
🟠 تعديل على المقال اكتمل                [ فتح ]
🟡 سؤال جديد من زائر                     [ رد ]
🟣 Reel تم رفعه وينتظر المعالجة          [ متابعة ]

عرض كل التحديثات
```

### ترتيب الأولوية

1. مقال ينتظر قرار العميل.
2. سؤال أو ملاحظة تحتاج ردًا.
3. تحديث على مقال طلب العميل تعديله.
4. فشل رفع فيديو/Reel أو اكتمال معالجته.
5. متابعة/تعليق جديد ومعلومات لا تتطلب قرارًا فوريًا.

## UI أولًا — Dummy Data أولًا

هذه مرحلة تصميم وتثبيت تجربة، وليست ربط API.

```text
UI Components + Screens
        ↓
Dummy data / event fixtures
        ↓
مراجعة العميل واعتماد الـUX
        ↓
Data adapter واحد
        ↓
Real API لاحقًا
```

### القاعدة التقنية

- الشاشات لا تعرف API مباشرًا.
- كل شاشة تقرأ من repository / adapter ثابت.
- الآن: `MockConsoleRepository` يعيد dummy data.
- لاحقًا: `ApiConsoleRepository` يعيد نفس الـtypes من API.
- تغيير مصدر البيانات لا يغير UI أو navigation أو business flow.

---

## ما لا ندخله الآن

- لوحة analytics كاملة.
- محرر صفحات أو SEO أو إعدادات موقع معقدة.
- فواتير وإدارة اشتراكات مفصلة.
- bulk actions، export، وحذف جماعي.
- Media library كاملة؛ نبدأ بالرفع فقط.
- كل صفحات الكونسل الموجودة اليوم.

---

## قرارات نحتاجها منك قبل التصميم

1. عند «طلب تعديل المقال»: هل العميل يكتب ملاحظة عامة، أم يعلّق على جزء محدد من المقال، أم الاثنان؟
2. نثبت catalog النهائي للأحداث: أي حدث فوري، وأي حدث يظهر فقط/يلخّص في التحديثات.
3. «ملاحظات العميل»: هل هي تعليقات على المقال، أم رسائل بين العميل وفريق مودونتي، أم كلاهما؟
4. المتابعون: هل المطلوب رؤية الاسم فقط، أم التواصل معهم، أم أرقام نمو فقط؟
5. رفع Reel/Video: هل العميل يرفع ملفًا خامًا أم رابطًا أم كليهما؟

```text
تسجيل الدخول → التحديثات → قائمة المقالات → مراجعة مقال → طلب تعديل / اعتماد
```

بعد اعتمادها نضيف:

