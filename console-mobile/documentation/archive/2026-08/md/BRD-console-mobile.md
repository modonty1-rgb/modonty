# BRD — تطبيق مودونتي كونسول للموبايل

**الحالة:** مسودة للنقاش — لا يبدأ التنفيذ قبل اعتمادها  
**المنتج:** `@modonty/console-mobile`  
**المنصات المستهدفة:** Android وiOS  
**التقنية المقترحة:** Expo + React Native + TypeScript + Expo Router  
**تاريخ الدراسة:** 27 أغسطس 2026

---

## 1. ملخص القرار

مودونتي كونسول هو مساحة العميل لإدارة حضوره، محتواه، جمهوره، وحجوزاته. النسخة الحالية هي تطبيق Next.js ويب، وتضم **34 مسارًا مرئيًا** و**21 ملف Server Actions** موزعة على أكثر من 25 مجالًا.

قرار هذا الـBRD: نبني تطبيق موبايل مستقلًا داخل نفس monorepo، يخدم عمليات العميل المتكررة والسريعة من الجوال. لا ننقل واجهة الويب كما هي، ولا نصنع WebView. نعيد بناء تجربة Native مع API مخصص للموبايل، ونبقي الأدوات التحريرية الثقيلة أو الإدارية المعقدة على الويب حتى يثبت احتياجها على الموبايل.

**نجاح النسخة الأولى لا يعني نقل كل الكونسل.** يعني أن العميل يستطيع، من هاتفه، رؤية ما يحتاج إجراءً، متابعة الحجوزات والرسائل، واتخاذ قرار أو إجراء أساسي بثقة وسرعة.

---

## 2. ما تمت دراسته في الكونسل الحالي

### 2.1 التقنية والوصول

- التطبيق الحالي: Next.js 16 + React 19 + Prisma / MongoDB + NextAuth credentials.
- تسجيل الدخول الحالي بالبريد أو `client slug` وكلمة المرور.
- Session الحالية JWT، مدتها 30 يومًا، وتحمل `clientId` واسم وslug العميل.
- يوجد دخول إداري بانتحال العميل عبر ticket موقع ومؤقت.
- كل Server Action حساس يتحقق من هوية العميل، ثم يقيّد الاستعلام بـ`clientId`؛ هذا السلوك يجب أن يبقى قاعدة غير قابلة للتنازل في Mobile API.
- الـAPI الظاهر اليوم تحت `/api/v1` مخصص في الغالب لسحب المقالات المنشورة إلى مواقع العملاء، وليس API مصادَقًا عليه لتطبيق الموبايل.

### 2.2 ما يراه العميل اليوم

| المجال | الموجود في Console web | طبيعة الاستخدام |
|---|---|---|
| لوحة التحكم | KPIs، عناصر تحتاج إجراء، أداء، جمهور، رسوم، نشاط أخير | قراءة واتخاذ قرار |
| المقالات | موافقة/إدارة/تفاصيل/Preview ومقالات الموقع | متابعة وموافقة؛ تحرير طويل |
| الحجوزات | قائمة، حالات، تأكيد وقت، حذف وعمليات جماعية | عالي الأولوية ومناسب للموبايل |
| Leads | قائمة، KPIs، تحديث score | عالي الأولوية للمتابعة |
| الدعم | رسائل، تغيير حالة، رد، bulk actions | عالي الأولوية ومناسب للموبايل |
| التفاعل | تعليقات، أسئلة، تعليقات/مراجعات العملاء، موافقة/رفض | مناسب للموبايل كتصفية إجراء |
| الجمهور | مشتركون، حذف/إلغاء اشتراك/export | متابعة؛ export يبقى ويب |
| المحتوى المرئي | Gallery، Reels، Videos، Media | مراجعة ورفع بسيط؛ إدارة كثيفة لاحقًا |
| الموقع | موقعي، صفحات الموقع، محتوى الصفحة، FAQ الصفحة | إعدادات/محرر؛ ويب أولًا |
| النشاط | Profile، SEO، keywords، competitors، campaigns، site health | قراءة مختصرة؛ إعدادات متقدمة ويب |
| الحساب | فواتير، اشتراك، إعدادات، Telegram | قراءة وإجراءات حسابية محدودة |

### 2.3 ملاحظات مؤثرة على المنتج

1. المقالات وFAQ هما المساران المثبتان أعلى navigation الحالية؛ المقالات موصوفة في الكود كوجهة يومية للعميل.
2. الكونسل يحسب شارات انتظار وحالات جديدة للحجوزات، leads، رسائل الدعم، الأسئلة، التعليقات، المراجعات، المحتوى والـmedia. هذا هو أساس شاشة **«تحتاج إجراء»** في التطبيق.
3. الكونسل يملك حالات بيانات خاصة بالعميل: خطة/اشتراك، فواتير غير مدفوعة، YMYL completion، وإمكان نشر مقالات موقع العميل. يجب ألا تتسرب بين العملاء.
4. لا توجد Mobile API متكاملة حاليًا؛ Server Actions لا يمكن ولا يجب استدعاؤها من React Native.

## 3. المشكلة والفرصة

### المشكلة

عميل الكونسل يتابع غالبًا من هاتفه، لكن الويب الحالي مبني حول sidebar طويل وجداول وإدخالات متعددة. الوصول إلى خبر جديد أو حجز أو رسالة يتطلب فتح المتصفح والتنقل داخل لوحة كثيفة. لا يوجد تنبيه Native يقود العميل مباشرة إلى العنصر المطلوب.

### الفرصة

نجعل التطبيق «مركز متابعة العميل»: يظهر أهم حدث، يعطي إجراءً واحدًا واضحًا، ثم يفتح التفاصيل عند الحاجة. هذا يرفع سرعة الاستجابة للحجز والـlead والتعليق ويقلل فقدان الفرص، مع إبقاء الويب للمحررات والتشغيل الإداري العميق.

## 4. المستخدمون والصلاحيات

### المستخدم الأساسي — عميل مودونتي

- مالك نشاط أو فريق عميل، مسجّل بحساب console.
- يرى **بيانات clientId الخاص به فقط**.
- أهم مهامه: متابعة حجوزات/Leads/رسائل، اعتماد محتوى، قراءة الأداء، تحديث معلومات بسيطة.

### مستخدم إداري منظم

- الانتحال الإداري موجود في الويب الحالي.
- **قرار مقترح للنسخة الأولى:** لا نفعّل انتحال admin في تطبيق العميل. يظل في admin/web حتى نحدد متطلبات التدقيق والموافقة والأمان للموبايل.

### قاعدة التفويض

كل endpoint يعيد تعريف العميل من access token على السيرفر. لا يقبل `clientId` مرسلاً من التطبيق كمرجع ثقة، ولا يعيد أي record لا يملك نفس `clientId`.

## 5. أهداف العمل وقياس النجاح

| هدف | قياس مقترح |
|---|---|
| تقليل زمن الاستجابة | زمن فتح/معالجة حجز أو lead من وصول التنبيه |
| عدم فقدان طلب جديد | نسبة الحجوزات وleads التي فتحت خلال 24 ساعة |
| جعل التطبيق عادة متابعة | مستخدمون نشطون أسبوعيًا، وعدد الجلسات لكل عميل |
| إجراء صحيح وآمن | نسبة نجاح mutations، أخطاء authorization = صفر |
| أداء جيد | زمن فتح أول شاشة، زمن إظهار قائمة الحجوزات، crash-free sessions |

**الأرقام المستهدفة لا تُثبت الآن**؛ نحتاج baseline من console/web وقرار business قبل الإطلاق الداخلي.

## 6. نطاق المنتج

### 6.1 MVP — داخل النطاق

#### A. الحساب والوصول

- دخول بالبريد أو slug + كلمة مرور.
- استعادة session، logout، انتهاء الجلسة، وربط آمن مع SecureStore.
- صفحة مساعدة عند فشل الدخول.
- عرض اسم العميل وخطته بصورة غير قابلة للتحرير في البداية.

#### B. الرئيسية — «اليوم»

- تحية العميل وملخص قصير.
- قائمة مرتبة حسب الأولوية: حجز جديد، lead جديد، رسالة دعم، محتوى/تعليق يحتاج قرارًا، تنبيه اشتراك.
- KPIs مقتصرة على معلومات قابلة للتنفيذ: حجوزات جديدة، leads، رسائل، عناصر انتظار.
- نشاط أخير موجز وروابط deep-link للتفاصيل.

#### C. الحجوزات

- قائمة وفرز حسب: جديد، تم التواصل، مكتمل، مؤرشف.
- تفاصيل الحجز وبيانات التواصل المتاحة حاليًا في الكونسل.
- تغيير الحالة.
- تعيين/إزالة وقت التأكيد.
- تنبيه عند حجز جديد وفتح مباشر لصفحة الحجز.
- لا bulk actions في أول نسخة إلا إذا أثبتت الدراسة التشغيلية ضرورتها.

#### D. صندوق المتابعة

- دمج ذكي، لا دمج بيانات عشوائي: Leads، رسائل الدعم، تعليقات/أسئلة ومراجعات تنتظر قرارًا.
- تبويبات/filters واضحة حسب النوع والحالة.
- الإجراءات المسموحة لكل نوع: رد، موافقة، رفض، تغيير حالة، أو فتح الويب عند تعقيد الإجراء.

#### E. المحتوى

- قائمة المقالات وحالاتها، خصوصًا pending approval.
- معاينة آمنة للمقال ومعلومات الأداء الأساسية عند توفرها.
- اعتماد/رفض فقط حين تكون قواعد المقال الحالية تدعم ذلك.
- رابط «فتح المحرر على الويب» للتحرير الطويل أو المعقد.

#### F. الحساب والإشعارات

- ملف العميل المختصر، رابط الصفحة العامة، الخطة، حالة الاشتراك والفواتير المفتوحة.
- إعدادات push داخل التطبيق.
- ربط device push token بالعميل والمستخدم، وإلغاء الربط عند logout.

### 6.2 لاحقًا بعد MVP

- Media/Gallery/Reels/Videos: استعراض ثم رفع بسيط.
- Analytics: cards وقراءة trends، لا لوحات رسوم معقدة كاملة.
- Subscribers: استعراض وحالة؛ export على الويب.
- FAQ وإدارة الأسئلة كاملة.
- حملات وUTM.
- Site Health كـsummary مع open-web للتفاصيل.
- Telegram preferences إذا ثبت أنه سلوك يومي للمستخدم.

### 6.3 ويب فقط مبدئيًا

| المجال | السبب |
|---|---|
| محرر المحتوى/الصفحات الكامل | إدخال طويل، تعدد حقول، ومعاينة دقيقة |
| Page blocks وsite pages | أدوات تخطيط ومحتوى لا تناسب شاشة الهاتف في v1 |
| SEO intake، keywords، competitors | كثافة نماذج وتحليل؛ قيمة يومية ضعيفة على الموبايل |
| إدارة الفواتير التفصيلية | حساسية مالية، تنزيلات، وقرارات محاسبية |
| Bulk delete/export | خطر تنفيذ غير مقصود؛ يمكن إضافته لاحقًا بضوابط |
| انتحال admin | يحتاج audit trail ومتطلبات أمنية خاصة |

## 7. Information Architecture للموبايل

### Bottom tabs الثابتة — خمس وجهات فقط

1. **اليوم** — dashboard/action center.
2. **الحجوزات** — متابعة الطلبات والمواعيد.
3. **المتابعة** — leads، رسائل، تعليقات وأسئلة تحتاج إجراء.
4. **المحتوى** — مقالات وحالات موافقة.
5. **حسابي** — الملف والخطة والإعدادات والدعم.

### Stack screens

```text
تسجيل الدخول
└─ Tabs
   ├─ اليوم
   │  └─ تفاصيل عنصر يحتاج إجراء
   ├─ الحجوزات
   │  └─ تفاصيل الحجز
   ├─ المتابعة
   │  ├─ تفاصيل Lead
   │  ├─ تفاصيل رسالة دعم
   │  └─ مراجعة تعليق / سؤال / Review
   ├─ المحتوى
   │  └─ معاينة/قرار مقال
   └─ حسابي
      ├─ الاشتراك والفواتير
      ├─ الإشعارات
      └─ الدعم
```

**قاعدة:** الـtab bar للتنقل بين وجهات ثابتة فقط. إجراءات مثل «اتصل»، «اعتمد»، «احجز وقتًا»، أو «رد» تكون CTA داخل الصفحة أو bottom sheet، وليست tabs.

## 8. المتطلبات الوظيفية التفصيلية

### FR-01 — الهوية والجلسة

- يجب أن يستطيع العميل تسجيل الدخول بالبريد أو slug وكلمة المرور كما هو في الويب.
- يجب أن تتحقق الخوادم من credentials وتصدر access token قصير العمر وrefresh token قابل للتدوير.
- يجب حفظ الأسرار في native secure storage فقط، لا AsyncStorage.
- يجب إبطال الجلسة محليًا وخادميًا عند logout أو اكتشاف refresh غير صالح.

### FR-02 — العزل بين العملاء

- لا يحدد التطبيق clientId في query/route للوصول إلى بيانات خاصة.
- يجب أن تشتق طبقة API clientId من token وتقيّد كل query/mutation به.
- يجب تسجيل محاولات الوصول المرفوضة ومراقبتها.

### FR-03 — Dashboard قابل للإجراء

- يعيد endpoint واحد summary خفيفًا: counts، أعلى action items، حالة الحساب المختصرة، وآخر نشاط.
- كل action item له نوع، priority، timestamp، target route وCTA متاح.
- لا ننقل الرسوم البيانية كاملة إلى أول شاشة؛ الأداء تفصيل اختياري لاحقًا.

### FR-04 — الحجوزات

- GET list مع cursor pagination وfilters للحالة.
- GET detail.
- PATCH status وconfirmedAt مع تحقق ملكية record وحالة انتقال مسموحة.
- mutation idempotency key عند التحديثات الحساسة لتفادي تكرار tap أو ضعف الشبكة.

### FR-05 — المتابعة والتفاعل

- كل قائمة تعرض النوع والحالة والوقت وصاحب الطلب/المرسل والسياق.
- الإجابة/الموافقة/الرفض تخضع لنفس validation الموجود في الويب.
- لا حذف نهائي من الموبايل في MVP.

### FR-06 — المقالات

- القائمة تميز: pending، approved/published، rejected حسب النموذج القائم.
- قرار الموافقة أو الرفض يقدم confirmation واضحًا، ثم ينعش summary والقائمة.
- التحرير والتحكم المتقدم ينتقل إلى الويب، مع deep link موثق.

### FR-07 — التنبيهات

- أنواع v1: حجز جديد، lead جديد، رسالة دعم جديدة، مقال/تعليق يحتاج قرارًا، تنبيه اشتراك مهم.
- كل push يتضمن route داخليًا ويدخل للعنصر الصحيح بعد tap.
- المستخدم يقدر يعطل فئات غير حرجة؛ لا يعطل notifications التشغيلية المهمة افتراضيًا بدون قرار business.

### FR-08 — حالات الشبكة

- loading skeleton، empty state، error state، وretry في كل list.
- cache للقراءة الأخيرة مع timestamp «آخر تحديث».
- mutations لا تعرض نجاحًا قبل تأكيد الخادم؛ عند الفشل تعرض إمكانية retry آمنة.

## 9. المتطلبات غير الوظيفية

### UX وRTL

- Arabic RTL هو الوضع الافتراضي، مع دعم إنجليزي لاحقًا دون كسر التخطيط.
- safe-area وkeyboard-aware layouts على Android وiOS.
- كل عناصر الضغط الأساسية 44–48pt/px عمليًا.
- لا محتوى تحت bottom tab أو CTA ثابت؛ مساحة سفلية محسوبة مع `safe-area-inset`.
- أفعال خطرة (حذف/رفض/أرشفة) تحتاج confirmation ودلالة واضحة.

### الأداء

- قوائم pagination بدل تحميل كل records.
- صور thumbnails بأحجام موبايل وcaching.
- dashboard endpoint مركب لتفادي سلسلة network calls عند الفتح.
- لا تحمّل مكتبات الرسوم أو محررات المحتوى في bundle الـMVP.

### الأمان والخصوصية

- HTTPS فقط؛ عدم تسجيل token أو كلمات المرور أو PII في logs أو analytics.
- refresh-token rotation وdevice registration قابل للإبطال.
- rate limits وmonitoring على auth وmutations.
- audit log للـstatus changes والموافقات في مرحلة API implementation.

### الجودة

- اختبارات unit للـcontracts وحالات التحويل.
- integration tests لـAPI authorization وownership.
- E2E لمسارات: login، حجز، push deep link، logout.
- اختبار RTL، keyboard، offline، Android وiOS على أجهزة فعلية قبل preview.

## 10. هندسة الحل

### داخل monorepo

```text
MODONTY/
├─ console/                 # Next.js web، يستمر كما هو
├─ console-mobile/          # Expo app الجديدة
├─ shared/                  # Prisma/server code — لا يذهب إلى bundle الموبايل
└─ contracts/               # جديد لاحقًا: Zod DTOs/types بلا Node أو Prisma
```

### console-mobile

```text
src/
├─ app/              # Expo Router routes وlayouts فقط
├─ features/         # auth, dashboard, bookings, inbox, content, account
├─ ui/               # design system native
├─ services/         # API client, token refresh, upload, push
├─ store/            # session وcached UI state
├─ hooks/
└─ lib/
```

### API المقترحة

```text
console/app/api/mobile/v1/
├─ auth/login
├─ auth/refresh
├─ auth/logout
├─ me
├─ dashboard
├─ bookings
├─ bookings/[id]
├─ inbox
├─ leads/[id]
├─ support/[id]
├─ articles
├─ articles/[id]
├─ notification-devices
└─ notifications/preferences
```

**مبدأ فصل واضح:** route handlers تستدعي services server-side مشتركة؛ لا نستورد server actions من mobile، ولا نكرر business rules في React Native.

### المكتبات المبدئية

- Expo SDK حديث + TypeScript.
- Expo Router.
- TanStack Query للـserver cache وmutations.
- Expo SecureStore للجلسة.
- Expo Notifications بعد development build.
- Native SVG/icons من نظام Modonty؛ لا نعتمد Lucide إلا لسبب موثق.
- EAS Build / EAS Update للـpreview والإصدارات.

لا نثبت أي مكتبة قبل إنشاء skeleton والموافقة على هذا الـBRD؛ نتحقق من توافقها مع Expo SDK المختار وقت التنفيذ.

## 11. ترتيب التنفيذ المقترح

### المرحلة A — اعتماد المنتج (لا كود)

1. اعتماد هذا BRD وتثبيت MVP/non-MVP.
2. تحديد شخصيات العملاء وأنواع التنبيهات والأولوية.
3. رسم Mobile UI System الكامل وحالاته، ثم مراجعة الصور والتدفقات.
4. حسم سياسة login وreset password وsupport داخل التطبيق.

### المرحلة B — Foundation

1. إنشاء `console-mobile/` داخل workspace.
2. إعداد Expo, Router, RTL, themes, env separation, lint/test.
3. بناء UI primitives والحالات العامة دون ربط بيانات.
4. إعداد internal preview builds؛ لا App Store submission بعد.

### المرحلة C — API/Auth contract

1. تعريف `contracts/` لـsession، dashboard، bookings.
2. بناء Mobile API مصادق عليه واختبارات ownership.
3. Token lifecycle، logout، device registration.
4. logging وerror handling بدون PII.

### المرحلة D — أول Vertical Slice

```text
Login → اليوم → الحجوزات → تفاصيل الحجز → تغيير الحالة → إشعار نجاح
```

لا نفتح نطاق features أخرى حتى ينجح هذا المسار على Android وiOS وبيانات حقيقية غير حساسة.

### المرحلة E — MVP

1. Inbox/Leads/Support.
2. Content approvals.
3. Push notifications + deep links.
4. Account summary/settings.
5. QA شامل وinternal pilot مع عملاء مختارين.

### المرحلة F — القرار بعد pilot

- مراجعة الاستخدام الحقيقي ووقت الاستجابة للحجز والـlead.
- ترتيب المزايا التالية حسب الاستخدام لا حسب كثرة صفحات الويب.
- إضافة media/analytics/FAQ فقط عندما تدعمها البيانات.

## 12. المخاطر والضوابط

| الخطر | الضبط |
|---|---|
| تحويل التطبيق إلى نسخة ويب مضغوطة | نلتزم بـMVP action-first وويب للأدوات الثقيلة |
| تسريب بيانات عميل لآخر | token-derived clientId + ownership tests + audit logs |
| محاولة إعادة استخدام `shared` كاملًا | contracts منفصل بلا Prisma/Node |
| توسيع API بلا قواعد موحدة | services + Zod contracts + versioned Mobile API |
| تكرار mutation بسبب شبكة ضعيفة | idempotency وoptimistic UI محدود |
| إشعارات مزعجة | فئات واضحة، priority، preferences وقياس opt-out |
| تعقيد محررات الموبايل | open-web مؤقتًا، لا نسخ محرر سطح المكتب |
| اختلاف Android/iOS/RTL | أجهزة فعلية، E2E، safe-area/keyboard test matrix |

## 15. تحقق حي من تجربة عميل فعلية

**طريقة التحقق:** مراجعة read-only لحساب عميل حي في `console.modonty.com`، ومراجعة كود الكونسل ومساراته. لم تُغيّر أي حالة أو بيانات خلال هذه الدراسة.  
**تنبيه:** الحساب فُتح من سياق إداري منتحل للعميل؛ الأرقام أدناه دليل على نوع البيانات والتدفقات، وليست مؤشرات أداء عامة لكل العملاء.

### 15.1 ما ظهر للعميل الحي

- Dashboard يعطي ثلاث فئات واضحة بالفعل: عناصر تحتاج انتباهًا، أداء، وجمهور.
- الحساب المراجع يملك حجوزات واردة عبر «اترك رقمك» وWhatsApp، وتعليقات تنتظر قرارًا، ورسائل دعم وLeads.
- صفحة الحجوزات توفر تصفية بالقناة والحالة، بحثًا، مصدر الطلب، وقت الوصول، ثم إجراءات: تم التواصل / تم / أرشفة / حذف.
- صفحة الدعم توفر inbox وحالات: جديد / مقروء / تم الرد / مؤرشف، مع الرد والأرشفة والحذف.
- صفحة التعليقات توفر طابور مراجعة بإجراءات موافقة / رفض / حذف.
- صفحة المقالات تفصل بين بانتظار الموافقة، المجدولة، والمنشورة.
- الملف والإعدادات يحويان حقولًا كثيرة وإجراءات إدارة أعمق: بيانات النشاط، SEO، الاشتراك، Telegram، تفضيلات إشعارات وكلمة المرور.

### 15.2 اختبار عرض الهاتف — 390×844

واجهة الويب تستجيب تقنيًا للشاشة الصغيرة، لكنها ليست تطبيق متابعة موبايل مريحًا:

| الملاحظة المقاسة | الأثر على العميل | قرار تطبيق الموبايل |
|---|---|---|
| شاشة الحجوزات تصبح قائمة بطول يتجاوز 4,100px | متابعة 12 طلبًا تعني تمريرًا طويلًا وتكرار أزرار لكل صف | بطاقة حجز مختصرة + تفاصيل في شاشة مستقلة + إجراء رئيسي واحد ظاهر |
| فلاتر القنوات والحالات ارتفاعها 36px | أقل من الراحة العملية للإبهام | 48px للـfilters المهمة، وتحويل الفلاتر الثانوية إلى bottom sheet |
| checkbox وبعض عناصر الإدارة تقاس 16px | سهلة الخطأ وغير مناسبة للمهام اليومية | لا bulk selection في MVP؛ أفعال فردية واضحة |
| أيقونات أعلى الويب 40px و«خروج» 24px | الحد الأدنى أو أقل لبعض الأفعال | targets 44–48px، وlogout داخل الحساب لا أعلى كل شاشة |
| Dashboard على الهاتف يتجاوز 3,900px | الأداء والرسوم يزاحمان العمل العاجل | شاشة «اليوم» تبدأ بما يحتاج قرارًا؛ analytics ملخص ثانوي |
| Profile وSettings يمتدان لأكثر من 2,600px و3,300px | نماذج سطح مكتب طويلة | أقسام قصيرة قابلة للإجراء فقط؛ الباقي فتح على الويب |

### 15.3 الاستنتاج المنتجّي

أهم شيء يصطحبه العميل في جواله ليس «كل أدوات إدارة الموقع»، بل أربعة أنواع من الوقائع:

1. **فرصة تحتاج سرعة:** حجز جديد أو lead جديد، مع معرفة المصدر ووسيلة التواصل وإجراء تواصل سريع.
2. **رسالة تحتاج جوابًا:** دعم أو سؤال أو تعليق، مع سياق مختصر وقرار/رد آمن.
3. **محتوى يحتاج قرارًا:** مقال أو تعليق منتظر؛ موافقة أو رفض بعد معاينة قصيرة.
4. **تنبيه حالة الحساب:** اشتراك أو فاتورة أو اكتمال معلومة مهمة، من دون ملء كل شاشة الحساب.

الأداء، SEO، media، وصفحة النشاط قيمة للعميل، لكنها ليست دائمًا سببًا لفتح التطبيق من الهاتف. مكانها في التطبيق يكون **ملخصًا وروابط سياقية**، لا تبويبًا رئيسيًا في MVP.

## 16. إعادة ترتيب MVP بناءً على الدليل الحي

### ما يجب أن يكون في الهاتف دائمًا

| الأولوية | الحاجة | ما يفعله العميل في أقل عدد نقرات |
|---|---|---|
| P0 | حجز أو lead جديد | يرى من وصل، من أين، متى، ويغيّر الحالة أو يبدأ التواصل |
| P0 | رسالة دعم/سؤال يحتاج متابعة | يقرأ السياق ويرد أو يحدد «تم الرد» |
| P0 | عنصر بانتظار الموافقة | معاينة قصيرة ثم موافقة أو رفض مؤكد |
| P1 | ملخص «اليوم» | يرى فقط الـcounts والوقائع العاجلة ويفتح العنصر الصحيح |
| P1 | push + deep link | يفتح الإشعار مباشرة على الحجز/الرسالة/المقال الصحيح |
| P1 | حالة الحساب الحرجة | تنبيه واضح للخطة/الفاتورة/المعلومة الناقصة، مع مسار معالجة |
| P2 | أداء مختصر | مشاهدات، conversion، ونمو مختصر؛ التفاصيل على الويب |

### ما لا يدخل أول تطبيق موبايل

- bulk selection وbulk delete.
- export CSV.
- محرر المقالات أو الصفحة الكامل.
- SEO intake، keywords، competitors، site pages وpage blocks.
- إعدادات Telegram التقنية أو تغيير كلمة المرور من أول نسخة.
- الرسوم والتحليلات الموسعة.

### التبويبات بعد التحقق الحي

1. **اليوم** — كل ما يحتاج انتباهًا بترتيب الأولوية.
2. **الحجوزات** — الطلبات الواردة وحالاتها.
3. **الوارد** — Leads، الدعم، والأسئلة/التعليقات التي تحتاج قرارًا.
4. **المحتوى** — المقالات والاعتمادات فقط.
5. **حسابي** — الملف المختصر، التنبيهات، والخروج وفتح الويب.

### المسار الذي يجب إثباته أولًا

```text
إشعار حجز جديد → شاشة تفاصيل حجز → تواصل/تحديث الحالة → نجاح واضح → عودة إلى «اليوم» بعد انخفاض العداد
```

إذا كان هذا المسار سريعًا وآمنًا، التطبيق يحل مشكلة حقيقية حتى قبل إضافة كل بقية الكونسل.
